What you are building

A research assistant for AI papers. Every weekday it downloads new papers from arXiv, splits them into short passages, and indexes them. When you ask a question, it finds the most relevant passages and has a local language model write an answer that cites them. This pattern is called RAG (retrieval-augmented generation): the model retrieves facts first, then generates an answer from them, instead of answering from memory.

When a question comes in

Question→ FastAPI endpoint→ Guardrail: is it about AI research?→ OpenSearch: find passages→ Grade each passage→ Ollama writes the answer→ Verify it against the passages

In the background, every weekday

Airflow schedule→ Fetch papers from arXiv→ Parse PDFs→ Save metadata in PostgreSQL→ Split, embed, index in OpenSearch

If you want the one-page overview of every service first, read STACK_EXPLAINED.html in the reference repo.

How every module works

Each module page is split into days of about three hours. Every day follows the same seven steps:

StepWhat happens
1. Why it existsThe problem this layer solves, and what breaks without it.
2. ConceptsPlain-English explanations before any code.
3. WalkthroughReal code from the reference repo, explained line by line for core logic, block by block for glue.
4. BuildYou type your own version, following a written spec.
5. CheckpointA command to run and what you should see. Then commit.
6. Break itThings to break on purpose, so you learn what each error looks like and how to trace it.
7. Interview drillAt the end of the module: questions you answer to me in chat, with model answers hidden until you try.

Five rules

  1. Type, don't paste. Typing is how the code gets into your head. The code blocks have no copy buttons on purpose.
  2. Commit at every checkpoint. Your git history becomes proof you built it, and a safety net when you break things.
  3. Explain it back before moving on. If you can't explain a line without looking, you haven't learned it yet.
  4. Hints before answers. When stuck, open the hint first. If still stuck after 20 minutes, ask me.
  5. Read every error message fully. The last line usually says what went wrong; the lines above it say where.

Running both projects side by side

The reference project already uses ports 8000, 5432, 6379, 9200, and others on your laptop. Two programs can't listen on the same port, so your project adds 10000 to every port it publishes:

ServiceReference projectYour project
API800018000
PostgreSQL543215432
Redis637916379
OpenSearch920019200
Ollama1143421434
Memory Both full stacks together need a lot of RAM. From Module 3 onwards, stop the reference stack (docker compose stop in its folder) while you run yours, and start it again when you want to compare.

Talking about it in interviews

Be accurate about where the project came from. A framing that is honest and still strong:

"I built a production-style agentic RAG system over arXiv papers. I started from an open-source course, then rebuilt it from scratch myself, and added hallucination safeguards the course didn't have: deterministic citation checks, per-chunk relevance grading, and a groundedness check that withholds unsupported answers."

Interviewers will probe whatever you claim. By Module 9 you'll be able to go as deep as they want on any layer, because you'll have built each one twice: once by reading, once by typing.
