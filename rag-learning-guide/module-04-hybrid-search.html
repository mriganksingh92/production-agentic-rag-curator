Day 1Why chunk, and word-based chunking

1. Why this matters

A paper is 5,000 to 15,000 words. You can't hand whole papers to a 1B-parameter model with a small context window, and an embedding of a whole paper is a blurry average of twenty topics. Retrieval works on passages: small enough to be about one thing, large enough to make sense alone. How you cut them decides what the rest of the system can find.

2. Concepts

TermMeaning
ChunkOne passage of a paper, indexed as one OpenSearch document.
Chunk sizeTarget length. Here measured in words: 600. (Many systems count tokens instead; words are simpler and close enough.)
OverlapWords repeated at the start of the next chunk: 100. A sentence cut at a boundary still appears whole in one of the two chunks.
StrideHow far each chunk starts after the previous one: chunk size − overlap = 500 words.
Minimum chunk size100 words. Below this a passage is too short to be useful on its own.
The trade-off. Small chunks are precise (a hit points at exactly the right paragraph) but lose context ("it" and "this method" lose their referents). Large chunks keep context but dilute the match and use more of the LLM's context window per hit. 600/100 is the course's choice; it's a tunable, not a law. Expect an interviewer to ask how you'd choose it: measure retrieval quality on real questions.

You already wrote a character-based chunker with overlap in Module 0 (playground/wrappers.py). Today's is the same loop over words, with metadata attached to each piece.

Day 2Section-aware chunking

1. Why this matters

Cutting every 500 words ignores the paper's structure: a chunk can start mid-way through the Method and end in the Results. Docling (Module 2) already gave you the sections. Chunking along them produces passages that are about one thing, labelled with where they came from. And a chunk that starts "Section: Experiments" after the paper's title and abstract carries its own context.

2. Concepts

The reference's hybrid strategy, per section, after filtering out junk:

Section lengthWhat happens
Under 100 wordsBuffered and combined with neighbouring small sections into one chunk.
100 to 800 wordsOne chunk: header + Section: title + the section.
Over 800 wordsSplit with chunk_text (600/100), each piece prefixed with the header, titled ... (Part N).
No sections at allFall back to chunk_text on the full text.

The header is "{title}\n\nAbstract: {abstract}\n\n", added to every section chunk. That's why every chunk matches the paper's title words, and why a chunk is often 150–250 words longer than its section.

Day 3Embeddings and the Jina client

1. Why this matters

BM25 only matches words. Ask "why do LLMs make things up?" and it can't find a passage about "hallucination" that never uses your words. An embedding represents meaning as numbers, so similar meanings end up close together even with no words in common.

2. Concepts

TermMeaning
VectorA list of numbers, like [0.12, -0.03, ...]. Think of it as a point, or an arrow from the origin, in a space with that many dimensions.
EmbeddingA vector produced by a neural network from text, trained so that texts with similar meaning get nearby vectors.
DimensionsThe vector's length. Jina v3 gives 1024 here, which must match "dimension": 1024 in the mapping.
Cosine similarityThe cosine of the angle between two arrows: 1 = same direction (same meaning), 0 = unrelated, −1 = opposite. It ignores length, so a long and a short text about the same thing still match.
cos(a, b) = (a1*b1 + a2*b2 + ... + an*bn) / (|a| * |b|)       |a| = sqrt(a1² + ... + an²)

a = [1, 0]   b = [1, 1]   cos = (1*1 + 0*1) / (1 * 1.414) = 0.707   (45 degrees apart)

Jina AI is a hosted embeddings API: you POST text, it returns vectors. Its v3 model is asymmetric: it embeds a question (task: "retrieval.query") differently from a passage (task: "retrieval.passage"), because a short question and the paragraph that answers it look nothing alike on the surface. Mixing the tasks up quietly degrades results.

Two proxy problems, two fixes Your corporate proxy re-signs HTTPS. Python's httpx trusts only certifi's certificate bundle, not Windows'. Inside Docker, the reference Dockerfile appends the corporate root to certifi's bundle (you copied that in Module 1). On your laptop, the same call fails with [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate. The fix is to build a bundle file and point SSL_CERT_FILE at it, which httpx honours. Both were verified on this machine this week.

Day 4Vector search and hybrid search with RRF

1. Why this matters

BM25 is excellent at exact terms: model names, acronyms, arXiv IDs. Vectors are excellent at meaning and paraphrase, but fuzzy about exact terms. Each fails where the other succeeds, so production retrieval usually runs both and merges the results. That merge is today.

2. Concepts

Finding nearest vectors fast: HNSW

Comparing a query vector to every chunk vector is exact but slow at millions of chunks. Approximate nearest neighbour (ANN) search trades a little accuracy for a lot of speed. HNSW (Hierarchical Navigable Small World) builds a graph where each vector links to its near neighbours, with sparse "express" layers on top. A search starts at the top, hops toward the query, and drops down a layer at a time, like motorway, then main road, then side street. The mapping's parameters: m: 16 links per vector (more = better recall, more memory); ef_construction: 512 how hard it searches for good links while building (higher = better graph, slower indexing). engine: nmslib is the library doing it; space_type: cosinesimil ranks by cosine similarity.

Why you can't just add the scores

BM25 scores are unbounded (5, 25, whatever the query produces). Vector scores live on a small fixed range. Adding them lets BM25 dominate. Normalising them is fragile. Reciprocal Rank Fusion (RRF) ignores scores and uses only positions: 

RRF(chunk) = sum over each result list of  1 / (k + rank)        k = 60 (rank_constant), rank starts at 1

rank 1 in one list only:        1/61           = 0.0164
rank 1 in both lists:           1/61 + 1/61    = 0.0328
rank 1 in BM25, rank 5 vector:  1/61 + 1/65    = 0.0318

That's why Module 0's hybrid results had scores around 0.016: they're RRF scores. A chunk found by both methods beats a chunk found by only one, even if that one ranked it first. k = 60 flattens the difference between rank 1 and rank 5, so no single list dominates.

OpenSearch runs this for you with a search pipeline: a named set of steps applied to search results. The hybrid query runs its sub-queries separately, and the pipeline's score-ranker-processor fuses them with RRF before returning.

Interview drill

Answer each question out loud or in writing before opening the model answer. Then message me "Drill me on Module 4" and I'll ask them in a different order, with follow-ups.

1. Why chunk at all? How did you choose 600 words with 100 overlap?
Whole papers are too long for the LLM's context and make blurry embeddings; retrieval should return a passage about one thing. 600/100 came from the course; it balances precision against context. The honest answer on choosing: it's a hyperparameter you tune by measuring retrieval quality on real questions, trading precision (smaller) against context (larger) and index size (more chunks with more overlap).
2. What does section-aware chunking do that fixed-size chunking doesn't?
Chunks follow the paper's structure: sections of 100–800 words become one chunk, small ones are merged, large ones split into parts, and author blocks and duplicate abstracts are dropped. Every chunk gets a title-plus-abstract header, so it carries its own context and is labelled with its section. Weakness I found: reference lists aren't filtered, so "References (Part 1)" chunks rank high for keyword queries.
3. What is an embedding, and why cosine similarity?
A vector from a neural network, trained so similar meanings land close together. Cosine similarity compares direction, not length, so a short and a long text about the same topic still match; 1 means same direction, 0 unrelated. Our vectors have 1024 dimensions, and the mapping must declare the same number.
4. Why does Jina have separate query and passage tasks?
Asymmetric retrieval: a short question and the paragraph that answers it look different, so the model embeds each side in a way that makes matching pairs close. Using the wrong task doesn't error; it just quietly lowers quality, which is why it's worth a unit test.
5. Explain HNSW and its two parameters in this mapping.
An approximate nearest-neighbour index: a layered graph where each vector links to near neighbours; search starts in sparse upper layers and descends, visiting a small fraction of vectors. m = 16 links per node (recall vs memory); ef_construction = 512 effort when building links (graph quality vs indexing time). Approximate means it can occasionally miss the true nearest.
6. Write the RRF formula. Why are hybrid scores around 0.016?
Sum over result lists of 1 / (k + rank), k = 60. Rank 1 in one list gives 1/61 ≈ 0.0164; rank 1 in both gives ≈ 0.0328. It uses positions only, so BM25's unbounded scores and vector scores never need normalising, and a chunk found by both methods wins.
7. How does OpenSearch execute a hybrid query here?
A hybrid query holds two sub-queries, the BM25 bool/multi_match and a knn, each fetching size * 2 candidates. The request names a search pipeline, hybrid-rrf-pipeline, whose score-ranker-processor fuses the two ranked lists with RRF. The client then drops hits under min_score.
8. What happens when Jina is down, at search time and at indexing time?
Search: the router catches the embedding error and falls back to BM25, returning search_mode: "bm25". Indexing: after the retry loop gives up, index_paper catches the exception and counts an error; the batch and the Airflow task still succeed. And because old chunks are deleted first with replace_existing, those papers vanish from the index until the next successful run. Needs monitoring on total_errors.
9. Describe the Jina retry policy and why it has each piece.
Up to 6 attempts on 429 and 5xx; other errors raise immediately because they'd fail the same way. Exponential backoff (2, 4, 8, 16, 30 s) gives the service time to recover; Retry-After is honoured when present; random jitter avoids many clients retrying in sync. It uses asyncio.sleep so the event loop isn't blocked. It was added this week because the free tier's rate limit was losing whole papers.
10. Name two bugs or gaps you found in the reference search code.
Any two of: the RRF pipeline existence check uses the ingest pipeline API for a search pipeline, so it re-creates it every startup and force never deletes; hybrid mode ignores from_ and latest, so pagination and date sorting silently do nothing; chunk_text's short-text branch calls _reconstruct_text with two arguments (TypeError); combined chunks contain literal \n\n characters; pdf_url and section_name are always null because the index doesn't store them under those names.
11. The DAG runs daily. How do papers already in Postgres get indexed?
They don't, by the DAG: it indexes only papers created by that run (or in the last day). Existing papers need a backfill, which I run with a one-off script calling the same HybridIndexingService.index_papers_batch(..., replace_existing=True). Incremental and backfill share code, so they can't drift apart.
12. When would BM25 beat vectors, and vice versa? What did your comparison show?
BM25 wins on exact tokens: model names, acronyms, IDs, rare terms. Vectors win on paraphrase and synonyms, when the question uses different words from the passage. Hybrid is robust to both. Then give your own three sentences from compare_search.py, with a concrete query each.
13. Why is make_embeddings_client not cached like the OpenSearch factory?
It wraps an httpx.AsyncClient, which is tied to the event loop it runs on. Airflow tasks call asyncio.run, creating and closing a loop each time, so a cached client would be unusable ("closed") on the next run. The OpenSearch client is synchronous, so a singleton is safe.
