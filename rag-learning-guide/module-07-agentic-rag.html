Day 1Agents versus pipelines, and a toy LangGraph graph

1. Why this matters

Your Module 5 RAG endpoint is a pipeline: a fixed sequence of steps that runs the same way for every question. Ask it "what's the weather?" and it still searches arXiv papers and asks the LLM to answer from them. Retrieve bad chunks, and it answers from bad chunks anyway. An agent lets the program choose its next step based on what just happened. Interviewers ask about this constantly, and the honest answer ("it's a graph of steps with LLM-made decisions at the branches") is much more convincing than buzzwords.

2. Concepts

Agent, in this project's sense

"Agent" is used loosely in industry. Here it means: an LLM-driven program whose control flow has branches (it can refuse, or answer) and loops (it can retry retrieval with a better query), with a hard limit on how many times it loops. It isn't a free-roaming assistant: every possible path is drawn in advance. That's deliberate. A drawn graph is testable and debuggable; "let the LLM figure it out" isn't.

LangGraph vocabulary

TermMeaning
StateA dictionary shared by every step. Defined as a TypedDict: a dict whose keys and value types are declared.
NodeA function that receives the state and returns a dict of updates (only the keys it changes).
Edge"After node A, run node B." Always taken.
Conditional edgeA function that looks at the state and returns the name of the next node.
START, ENDSpecial node names for where the graph begins and stops.
ReducerA rule for merging a node's update into the state. Default: replace. add_messages: append.
compile()Checks the graph (no dangling edges) and returns a runnable object with invoke / ainvoke.
Runtime contextRead-only objects for this run (clients, settings), declared with context_schema. Not part of the state.

Reducers and add_messages

If two nodes both return {"messages": [...]}, should the second replace the first, or add to it? For a chat history you want "add". You declare that on the state key: messages: Annotated[list, add_messages]. Annotated[type, extra] attaches extra information to a type hint; LangGraph reads the extra as the reducer. Keys without a reducer are simply overwritten.

Messages

LangChain represents a conversation as a list of message objects: HumanMessage (the user), AIMessage (the model; can carry tool_calls), ToolMessage (a tool's result), and SystemMessage (instructions). The agent's whole conversation lives in state["messages"].

Runtime context versus state

State changes as the graph runs and is what nodes communicate through. Context is fixed for a run: the Ollama client, the OpenSearch client, the model name, top_k. In LangGraph 1.0 you declare it with StateGraph(State, context_schema=Context), pass it with graph.ainvoke(inputs, context=Context(...)), and a node reads it through a second parameter: async def node(state, runtime: Runtime[Context]), then runtime.context.ollama_client. Keeping live clients out of the state keeps the state small and printable.

Step B: write playground/toy_graph.py

A "triage" graph: questions mentioning papers get answered; anything else gets refused. No LLM, so it runs instantly.

  1. ToyState, a TypedDict: messages: Annotated[list, add_messages], route: str, attempts: int.
  2. ToyContext, a dataclass: keyword: str = "paper", max_attempts: int = 2.
  3. classify(state, runtime: Runtime[ToyContext]) -> dict: reads the last message's content; returns {"route": "answer"} if runtime.context.keyword appears in it (case-insensitive), otherwise {"route": "refuse"}.

Day 2State, context, models, config, prompts, and the guardrail

1. Why this matters

Nodes only talk to each other through the state, read their clients from the context, and parse LLM replies with the Pydantic models. Get these four files right and every node becomes a short function. The guardrail is the first decision the agent makes: is this question even about research papers?

2. Concepts

Structured output

Asking an LLM "reply with JSON" and parsing its text is fragile. LangChain's llm.with_structured_output(Model) turns a Pydantic model into a JSON schema, asks the model to answer in that shape, and returns a validated instance of Model. If the reply doesn't match, you get an exception, which the nodes catch.

Getting a LangChain model from Ollama

OllamaClient from Module 5 talks to Ollama with raw httpx. LangChain nodes need a LangChain chat model object instead. Every HEAD node calls runtime.context.ollama_client.get_langchain_model(model=..., temperature=...), and then .with_structured_output(...) on the result.

The method the original code calls doesn't exist in the original code Run git show HEAD:src/services/ollama/client.py | Select-String "def ". HEAD's OllamaClient has health_check, list_models, generate, generate_stream, generate_rag_answer, and generate_rag_answer_stream, but no get_langchain_model. So in the original course code, every LLM call in the agent raised AttributeError, and each node's except quietly switched to its fallback. The working tree adds the method (def get_langchain_model(self, model: Optional[str] = None, temperature: float = 0.0, **kwargs), returning a cached ChatOllama). You'll write a simpler version of it. Lesson: a broad except can hide a bug that breaks every request.

Guardrail

A guardrail is a check that stops unwanted input or output. Here the LLM scores how related the question is to research papers (0–100). Below guardrail_threshold (60 in Context), the agent refuses politely instead of searching. It's cheap insurance: one short LLM call instead of a full retrieve-grade-generate run.

Day 3The retriever tool, the retrieve node, and query rewriting

1. Why this matters

This is where the agent actually searches. It does so through a tool, the standard way LLM frameworks let a model trigger code. Understanding tool calls is the most transferable skill in this module: every agent framework uses them.

2. Concepts

Tools and tool calls

A tool is a function wrapped with a name, a description, and an argument schema, via LangChain's @tool decorator. An AIMessage can carry tool_calls: a list like [{"name": "retrieve_papers", "args": {"query": "..."}, "id": "..."}]. The model doesn't run anything; it requests a call.

ToolNode and tools_condition

LangGraph's prebuilt ToolNode([tool]) is a node that reads the last AIMessage's tool_calls, runs the matching tools, and appends a ToolMessage with each result. tools_condition is a ready-made conditional edge: it returns "tools" if the last message has tool calls, otherwise END.

A closure-built tool

The tool needs the OpenSearch and Jina clients, but a tool's arguments are what the model supplies (just a query). So a factory function create_retriever_tool(opensearch_client, embeddings_client, top_k, use_hybrid) defines the tool inside itself; the inner function "closes over" the clients. That's a closure.

3. Walkthrough: real code

src/services/agents/tools.py (HEAD)

Read it block by block. The factory builds a @tool-decorated async function named retrieve_papers whose docstring is the description the model sees. Inside it: embed the query with the Jina client, call the OpenSearch client's unified search (hybrid or BM25), and turn each hit into a LangChain Document with the chunk text as page_content and paper details (arXiv ID, title, authors, score, PDF URL as source, section) in metadata. Day 4Grading, generating, and wiring the graph

1. Why this matters

Grading is what makes this "agentic" rather than a pipeline with extra steps: the agent judges its own retrieval before answering. Today you also wire every node into one graph and wrap it in a service class, the shape an interviewer will ask you to draw.

2. Concepts

LLM-as-judge

Using an LLM to evaluate something (here: "are these documents relevant to the question?") is called LLM-as-judge. It's convenient, but a small model is a weak judge. Keep that in mind; Module 8 is built on the consequences.

Service class and factory

AgenticRAGService owns the compiled graph and exposes one method, ask(...). A factory function make_agentic_rag_service(...) builds it from the clients, the same factory pattern as the other services.

Interview drill

Answer each question out loud or in writing before opening the model answer. Then message me "Drill me on Module 7".

1. What's the difference between your /ask pipeline and the agentic endpoint?
/ask always retrieves and generates. The agent is a graph with decisions: a guardrail can refuse, grading can send it back to rewrite the query and retrieve again, and a counter caps the retries. It's more robust to bad retrieval and off-topic questions, and several times slower because it makes more LLM calls.
2. Explain LangGraph's state, nodes, and edges.
State is a shared TypedDict. A node is a function that reads the state and returns only the keys it changes. Edges say what runs next; conditional edges run a function on the state to choose. START/END mark entry and exit, and compile() validates the graph and makes it runnable.
3. What is a reducer, and why does messages use add_messages?
A reducer decides how an update merges into the state. The default overwrites. add_messages appends (and updates messages with the same ID), so every node's message joins the conversation instead of replacing it.
4. Why keep clients in a runtime context rather than in the state?
The state is data that changes and gets logged or checkpointed; clients are live connections that don't change and can't be serialised. context_schema=Context gives every node typed access through runtime.context without polluting the state.
5. How do tool calls work, and what do ToolNode and tools_condition do?
An AIMessage can request calls (name, args, id); nothing runs until code executes them. ToolNode executes the requested tools and appends ToolMessages. tools_condition routes to the tool node if the last message has tool calls, else to END. In this project the retrieve node builds the tool call itself, because a 1B model is unreliable at doing it.
6. What stops the agent from looping forever?
retrieval_attempts in the state, compared with max_retrieval_attempts (2) in the context. At the limit the retrieve node returns a fallback message with no tool call, so the graph ends. LangGraph's recursion limit is a second safety net.
7. What does with_structured_output do, and what happens when a small model gets it wrong?
It converts a Pydantic model into a schema, asks the LLM for that shape, and returns a validated object. When validation or the call fails, the node's except takes over with a fallback. Which way each fallback leans is a design decision. In the original, the guardrail falls back to score 50 (refuse), but grading falls back to "any context over 50 characters is relevant" (answer), and generation returns an apology as the answer.
8. What is the guardrail and why use a score instead of yes/no?
An LLM check that the question is about research papers, before any retrieval. A 0–100 score lets you tune the threshold (60) in config without rewriting the prompt, and it's cheaper to refuse early than to run the whole graph.
9. How did you unit-test nodes that call an LLM?
A conftest fixture replaces the Ollama client with a MagicMock whose get_langchain_model returns a fake LLM; its with_structured_output(...).ainvoke is an AsyncMock whose return value each test sets. Tests are fast, deterministic, and assert on the node's returned updates. Separate tests cover the graph's shape and the endpoint with dependency_overrides.
10. Name the weaknesses of the original agent.
Whole-context grading with a single verdict; no verification of the answer against the sources; sources always empty because relevant_sources is never set; the request's model ignored; chunks_used reports top_k rather than reality. I fixed these in the hardening work.
11. Why is the agentic endpoint so slow on your laptop, and what would you change?
About six sequential LLM calls to a CPU-only model at tens of seconds each. Options: a GPU, a hosted model, fewer calls (skip the guardrail for obvious cases, grade with a cheaper heuristic first), caching, or streaming progress so the user sees work happening.
12. When would you not use an agent?
When the fixed pipeline already works: agents add latency, cost, and more ways to fail. Use one when inputs vary enough that deciding per request pays off, and always bound its loops and test its branches.
