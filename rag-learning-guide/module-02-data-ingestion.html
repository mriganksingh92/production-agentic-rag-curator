Day 1The arXiv API, Atom XML, and the client

1. Why this matters

arXiv is where AI papers appear first. Its API is free, old, and strict: it answers in XML, not JSON, and asks you to wait 3 seconds between requests. Every paper your RAG system will ever cite enters through this client, so it has to parse reliably and fail loudly.

2. Concepts

The query

One GET request to https://export.arxiv.org/api/query with these query parameters:

ParameterExampleMeaning
search_querycat:cs.AI AND submittedDate:[202609290000 TO 202609292359]Category cs.AI, submitted on 29 Sept 2026 (dates as YYYYMMDDHHMM)
start, max_results0, 15Pagination
sortBy, sortOrdersubmittedDate, descendingNewest first

Atom XML and namespaces

The answer is an Atom feed: XML with one <entry> per paper. XML namespaces let one document mix tag vocabularies without name clashes: xmlns="http://www.w3.org/2005/Atom" makes plain tags like <title> Atom tags, and xmlns:arxiv="..." means <arxiv:primary_category> belongs to arXiv's own vocabulary. When you search with Python's xml.etree.ElementTree, you must say which namespace you mean: entry.find("atom:title", namespaces) with namespaces = {"atom": "http://www.w3.org/2005/Atom", ...}. Forgetting this is the classic "why does find return None?" bug.

This is a real entry, fetched this morning (trimmed):

  <entry>

Day 2Rate limiting, retries with backoff, and PDF downloads

1. Why this matters

Networks fail, and polite clients don't hammer servers. arXiv asks for 3 seconds between calls and will block clients that ignore it. PDFs are several megabytes each, travel through your office proxy, and sometimes time out: the reference logs from this week show PDF download timeout (attempt 1/3) warnings. Retrying, waiting, and caching are what turn a flaky network into a reliable pipeline.

2. Concepts

TermMeaning
Rate limitingEnforcing a minimum gap between requests. Here: remember the last request time and sleep for the remainder.
RetryTry again after a failure that might be temporary (timeouts, 503). Don't retry errors that won't change (404).
BackoffWait longer after each failure so a struggling server can recover. Linear: 5 s, 10 s, 15 s. Exponential: 5 s, 10 s, 20 s, 40 s.
CacheKeep the downloaded file; next time, use it instead of downloading again.
Streaming downloadWrite the response to disk in chunks as it arrives, instead of holding the whole file in memory.

Day 3PDF parsing with Docling

1. Why this matters

The abstract is 200 words; the answer to a user's question is usually in the paper body. A PDF stores glyphs at positions on a page, not paragraphs, so "get the text" means reconstructing reading order, headings, and tables. Docling does this with machine-learning layout models. The sections it produces are what Module 4 cuts into chunks.

2. Concepts

TermMeaning
Layout analysisA model looks at each page image and labels regions: title, section header, paragraph, table, figure.
OCROptical character recognition: reading text from pixels. Only needed for scanned PDFs; arXiv PDFs have real text, so it's off (and very slow).
Table structureA second model that recovers rows and columns. On by default.
CPU-boundWork that keeps the processor busy instead of waiting. Parsing a paper on your CPU takes tens of seconds to minutes.
asyncio.to_threadRuns a normal (blocking) function in a worker thread and lets you await it, so the event loop stays free.

Docling depends on PyTorch, so it's heavy: about a gigabyte of packages, plus model files downloaded from Hugging Face on first use.

            raise PDFValidationError(f"PDF file not found: {pdf_path}")

Day 4The metadata fetcher: concurrency and per-paper errors

1. Why this matters

You have three parts: fetch, download-and-parse, store. The orchestrator runs them for a whole day's papers, as fast as the network and CPU allow, without letting one broken PDF sink the run. This is the code the Airflow task calls, and the logic behind lines like Pipeline completed in 924.2s: 15 papers, 11 PDFs, 4 errors in this week's logs.

2. Concepts

TermMeaning
SemaphoreA counter that limits how many tasks may be inside a block at once. async with semaphore: waits if the limit is reached.
gather(..., return_exceptions=True)Run all tasks; if one raises, put the exception object in its result slot instead of cancelling the rest.
PipeliningEach paper moves from download to parse on its own, so paper 1 can be parsing while papers 2–5 download.

Two different limits here: up to 5 downloads at once (network-bound, cheap to overlap) and 1 parse at a time (CPU-bound; running two Docling parses on a laptop just makes both slower and doubles memory).

        self.max_active_downloads = 0

        return self.papers

        self.active_downloads += 1
        self.max_active_downloads = max(self.max_active_downloads, self.active_downloads)
        await asyncio.sleep(self.download_seconds)
        self.active_downloads -= 1
        if paper.arxiv_id in self.failing_downloads:
            return None
        return Path(f"{paper.arxiv_id}.pdf")

Day 5Airflow: running the pipeline on a schedule

1. Why this matters

A script you remember to run isn't a pipeline. Airflow runs the ingestion every weekday at 6 a.m., retries failures, keeps logs per run, and shows what happened in a web UI. It's the industry-standard scheduler, and "how does your data get in?" is one of the first interview questions about any RAG system.

2. Concepts

TermMeaning
DAGDirected acyclic graph: a workflow of tasks with arrows between them and no loops. Defined in a Python file in the dags/ folder.
Task / operatorA task is one step. An operator is the kind of step: PythonOperator calls a function, BashOperator runs a shell command.
ScheduleWhen to run, often as a cron expression: "0 6 * * 1-5" = minute 0, hour 6 (UTC), every day of the month, every month, Monday to Friday.
start_date and catchupThe first date the DAG is valid. With catchup=True, Airflow would create a run for every missed interval since then; False runs only the latest.
Logical dateThe date a run "is for" (called execution_date in this code). A manual trigger gets the current time.
XCom"Cross-communication": small values one task stores and another reads, kept in Airflow's database. For counters, not for PDFs.
Scheduler, webserver, executorThe scheduler decides what should run; the executor runs it (LocalExecutor: as processes in the same container); the webserver is the UI.
Metadata databaseWhere Airflow stores runs, task states, XComs, and users. Here it's your rag_db, next to papers.

1. Walk me through how a paper gets from arXiv into your database.
At 6 a.m. on weekdays, Airflow runs setup >> fetch >> report. The fetch task computes yesterday's date and calls the metadata fetcher: the arXiv client queries cat:cs.AI with a submittedDate range and parses the Atom XML into ArxivPapers; each paper is downloaded (up to 5 at once, cached, retried) and parsed by Docling (1 at a time, in a worker thread); then every paper is upserted into Postgres through the repository, with parsed text where available. Counters go to XCom and the report task logs them.
2. Why do XML namespaces matter when parsing arXiv's response?
The feed declares Atom as the default namespace, so <entry> is really {http://www.w3.org/2005/Atom}entry. ElementTree's find("entry") without a namespace map silently returns nothing. The client passes {"atom": ..., "arxiv": ...} and searches atom:entry. A test that counts parsed entries catches the silent failure.
3. How does the client respect arXiv's rate limit, and what are the weaknesses?
It remembers the last request time and await asyncio.sleeps for the rest of the 3 seconds before the next API call; downloads always sleep the delay first. Weaknesses: the state is per client instance, and concurrent downloads each sleep independently, so five downloads can still start at nearly the same moment. A shared async lock or token bucket would enforce a true global rate.
4. Describe the download retry logic. Is it exponential backoff?
Up to 3 attempts; on a timeout or HTTP error it waits 5 × (attempt + 1) seconds (5, then 10) and retries, then raises a specific exception. Despite the comment, that's linear backoff. It also retries 404s, which can't succeed, and its partial-file cleanup is unreachable, so an interrupted download could be cached as a broken file. I'd use exponential backoff with jitter, retry only transient errors, and write to a temp file then rename.
5. What does Docling do that plain text extraction doesn't?
It runs layout models over each page to recover reading order and label regions as titles, section headers, paragraphs, and tables, so the output has structure. The parser walks the text elements and starts a new section at each header, producing titled sections that the chunker later uses. OCR is off because arXiv PDFs have embedded text.
6. Tell me about the "can't be used in 'await' expression" bug.
An upstream commit made DoclingParser.parse_pdf synchronous but the service still did await self.docling_parser.parse_pdf(...). Every parse succeeded, then awaiting the returned PdfContent raised a TypeError, so the 25 September run stored all 15 papers without text. The fix, await asyncio.to_thread(...), makes the call awaitable and runs the CPU-bound parse in a thread so downloads keep flowing. I have a test that fails if the call blocks the event loop.
7. Why two semaphores with different limits?
Downloads are I/O-bound: overlapping five of them mostly overlaps waiting. Parsing is CPU- and memory-heavy: on a laptop, two parallel Docling parses are slower per paper and double memory. The download slot is released before parsing, so the stages pipeline: one paper parses while others download.
8. How does one bad PDF not break the whole run? What's the catch in the counters?
asyncio.gather(..., return_exceptions=True) turns each paper's failure into a value, and storage wraps each upsert in its own try. Every paper is stored, with or without content. The catch: an exception during parsing replaces the whole result, so a successful download isn't counted. That's why a log can say 0/15 downloaded when the PDFs are on disk.
9. Why is ingestion idempotent, and why does that matter?
Papers are upserted by arxiv_id, and PDFs are cached on disk, so re-running a day updates rows instead of duplicating them and doesn't re-download. Airflow retries tasks (2 retries here) and people re-trigger runs; without idempotency every retry would create duplicates.
10. Explain DAG, task, operator, schedule, catchup, and XCom using this project.
The DAG arxiv_paper_ingestion is the workflow; its tasks are PythonOperators calling setup_environment, fetch_daily_papers, and generate_daily_report, chained with >>. The cron schedule 0 6 * * 1-5 runs weekdays at 06:00 UTC. catchup=False stops Airflow back-filling every weekday since the 2025 start date. The fetch task pushes its counters to XCom under fetch_results, and the report task pulls them.
11. Why did the Airflow image build keep failing, and how was it fixed?
pip reported hash mismatches on large wheels. The corporate TLS-inspecting proxy was intermittently corrupting big downloads; the packages were fine. The Dockerfile now uses a BuildKit pip cache mount so verified wheels persist, and a shell retry loop re-runs pip up to 8 or 12 times. It also vendors Airflow's constraints file because GitHub raw is blocked, and adds the corporate CA to certifi for runtime HTTPS.
12. How does the Airflow container run your application code without copying it into the image?
Compose bind-mounts ./src to /opt/airflow/src and ./airflow/dags to /opt/airflow/dags. common.py adds /opt/airflow to sys.path, so tasks import the same src.services... as the API. Edits take effect on the next run without a rebuild. The trade-off: the image doesn't pin the code version, and a broken save breaks the live DAG.
13. The same src/ runs in the API and in Airflow. What compatibility issue did that create?
Airflow 2.10 requires SQLAlchemy 1.4 (requirements-airflow.txt pins <2.0), while the API uses 2.x. The shared code must work on both: select(), session.scalar(), and sqlalchemy.orm.declarative_base exist in both versions. Anything 2.0-only in src/ would break ingestion.
