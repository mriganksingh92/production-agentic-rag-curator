Day 1Why RAG still hallucinates, and deterministic citation checks

1. Why this matters

A hallucination is output that sounds confident but is not supported by any source: a made-up fact, number, or reference. RAG (retrieval-augmented generation) was supposed to fix this by putting real passages in the prompt. It helps, but it does not force the model to use only those passages. A small model like llama3.2:1b has read millions of papers during training and will happily "remember" a citation that sounds right. For a research assistant, a fake citation is the worst possible bug: it looks exactly like a real one, and a user who trusts it wastes hours or repeats it.

What actually happened in this project this week
  • Plain /ask retrieved chunks from only 2609.30227 and 2609.30558, yet the answer cited 2304.06476 and 2305.08659. Neither was in the prompt. After the first fix, a later run caught and removed 2204.12176.
  • The first version of the hardened answer prompt said "cite papers like [arXiv:2301.00001]". The 1B model copied the example and cited 2301.00001, 2301.00002, and so on. The example was removed from the prompt.
  • With fake IDs gone, the model switched to author-style citations: "Park", "Rasmussen", "Yan et al.", none of whom wrote the retrieved papers. The LLM groundedness check (Day 3) passed an answer like that. An LLM judge is itself an LLM, and can be fooled by the same fluency that fooled the user.
  • An answer with hallucinated citations had been cached in Redis before the fix, so the same question kept returning it until the cache was flushed. (Module 6 covered that incident.)

Three design principles

  1. Deterministic checks before LLM judges. A deterministic check is ordinary code that always gives the same answer for the same input, like "is this arXiv ID in the list of retrieved IDs?". It is instant, free, and cannot be talked out of its answer. An LLM judge is a second model call that asks "is this answer supported?". It catches subtler problems but is slow, costs a call, and can be wrong. So run the cheap exact checks first, and use the LLM only for what code cannot check.
  2. Fail closed. When a safety step itself breaks (the grader throws an exception, the guardrail returns nothing), treat it as "not safe": exclude the chunk, withhold the answer, reject the question. The opposite, fail open, lets everything through when the check breaks, which is exactly when you most need it. The original course code failed open in two places; you'll fix both.
  3. Measure. "It feels better" is not evidence. You'll write a script that runs a fixed set of questions against both endpoints and counts answers, refusals, and removed citations (Day 4).

Regular expressions, the minimum you need

A regular expression (regex) is a pattern for matching text. Python's re module uses them. \d{4} means exactly four digits; \d{4,5} four or five; (?:...) is a group that is not captured; (...) is a captured group you can read back with match.group(1); ? after something makes it optional; \s* is any amount of whitespace; \b is a word boundary. pattern.sub(func, text) replaces every match with whatever func(match) returns, so returning "" deletes the match and returning match.group(0) keeps it.

_CITED_ID = re.compile(r"(?:arXiv:\s*)?(\d{4}\.\d{4,5})(?:v\d+)?", re.IGNORECASE)
 Matches an arXiv ID with an optional arXiv: prefix and optional version suffix. Group 1 is the bare ID, e.g. 2304.06476. Compiling once at import time avoids re-parsing the pattern on every call.
_AUTHOR_CITATION = re.compile(r"\b([A-Z][A-Za-z'\-]+)\s+et\s+al\b")
 Matches "Surname et al". Group 1 is the capitalised surname, e.g. Rasmussen.
_EMPTY_BRACKETS = re.compile(r"\s*[\[(][\s,;]*[\])]")
_DANGLING_SEPARATOR = re.compile(r"([\[(])\s*[,;]\s*|\s*[,;]\s*([\])])")
 Clean-up patterns. Deleting an ID from [arXiv:2304.06476] leaves []; from [arXiv:2609.30227, arXiv:2304.06476] it leaves a stray , . These remove the leftovers.

    return re.sub(r"v\d+$", "", arxiv_id.strip())

    def _drop_unverified(match: re.Match) -> str:
        if match.group(1) in allowed:
            return match.group(0)
        removed.add(match.group(1))
        return ""

    if removed:
        cleaned = _DANGLING_SEPARATOR.sub(lambda m: m.group(1) or m.group(2), cleaned)
        cleaned = _EMPTY_BRACKETS.sub("", cleaned)
    return cleaned, sorted(removed)
 Tidy up only if something was removed, so a clean answer is returned byte-for-byte unchanged. Returns a tuple: the cleaned answer, and the sorted removed IDs (sorted so tests and logs are stable).
def unverified_author_citations(answer, retrieved_authors) -> List[str]:
    known = {part.lower() for name in retrieved_authors for part in name.split()}
    return sorted({m.group(1) for m in _AUTHOR_CITATION.finditer(answer)
                   if m.group(1).lower() not in known})
 Every word of every retrieved author's name, lower-cased, becomes "known". Any "X et al." whose X is not known is returned. It does not edit the answer: you can't delete a sentence built around a fake author and keep it readable, so the caller decides (Day 3: withhold the whole answer).
Know the limits The ID regex also matches things like version numbers 2023.12345 in prose. The author check is lenient: splitting names into words means a surname matching any author's first name passes. These are deliberate trade-offs for a cheap first filter, and good interview material.

Hint: the tidy-up order

First turn [, x] into [x] and [x, ] into [x] (dangling separators), then delete brackets that contain only spaces, commas, or semicolons, together with the space before them. That is why "Shown in (2304.06476)." becomes "Shown in.".

Day 2Structured tool output and per-chunk grading

1. Why this matters

In Module 7 the retriever tool returned a list of documents, LangChain turned it into one string inside a ToolMessage, and the grading node read that string back. Two problems followed. First, once documents are flattened to text, the code can no longer ask "which paper did this chunk come from?", so it could not build a sources list (the agent returned empty sources). Second, the grader judged all chunks together with a single yes/no: one relevant chunk admitted the irrelevant ones, and then all of them went to the answer prompt. If grading crashed, the original code fell back to "relevant if the text is longer than 50 characters", which fails open.

2. Concepts

Content and artifact

A LangChain tool created with @tool(response_format="content_and_artifact") must return a tuple (content, artifact). The content is the text the LLM sees. The artifact is any Python object for your own code, and the LLM never sees it. When ToolNode runs the tool, it puts both into the ToolMessage: msg.content and msg.artifact. So the LLM gets readable excerpts, and the grading node gets real Document objects with metadata.

One subtlety: the artifact only appears when the tool is invoked with a full tool call (a dict with name, args, id, type: "tool_call"), which is what ToolNode does. Calling tool.ainvoke({"query": ...}) directly returns only the content string. The tests therefore invoke the tool the way ToolNode does.

Concurrent grading with asyncio.gather

await asyncio.gather(a(), b(), c()) starts all three coroutines and waits for all of them, returning results in the same order as the arguments (not completion order). That ordering lets you zip documents with their grades. On a single-CPU Ollama the calls may still be processed one after another, so this saves waiting time, not compute.

def get_latest_documents(messages: List) -> List[Document]:
    for msg in reversed(messages):
        if isinstance(msg, ToolMessage):
            return list(msg.artifact or [])
    return []

def format_documents(documents: List[Document]) -> str:

Day 3Verifying the answer, and exposing it in the API

1. Why this matters

Grading decides what goes into the prompt. Nothing so far checks what comes out. Today you add a final graph node, verify_answer, that inspects the draft answer before the user sees it, and you fix the gaps in the API response that Module 7 pointed out: empty sources, chunks_used hard-coded to top_k, a model field that was ignored, and a guardrail that let questions through when it had no result.

2. Concepts

Groundedness

An answer is grounded if every claim in it is stated in, or directly follows from, the source documents. Checking groundedness with a second LLM call is the "LLM-as-a-judge" pattern. It is useful but not trustworthy on its own: this week the judge passed an answer that cited invented authors. That is why the deterministic author check runs first and, when it fires, the judge is not even asked.

Refuse with something useful

When verification fails, the user gets a fixed refusal ("I won't guess") plus the list of relevant papers with URLs. The retrieval was still valuable; only the generated prose is untrusted. This is a common production pattern: degrade to what you can vouch for.

Day 4Measuring hallucination, and the price of safety

1. Why this matters

Every safeguard you added makes the system refuse more. A system that refuses everything never hallucinates and is useless. The only way to know where you are on that trade-off is to run the same questions through both endpoints and count. In an interview, "I measured it, and here is what I found, including what got worse" is far stronger than "I added guardrails".

2. Concepts

What an evaluation needs

  • A fixed question set that includes questions the system should answer (in scope) and questions it should refuse (out of scope).
  • Metrics you can compute automatically: answered versus refused, fabricated citations removed, latency.
  • Honest limits: five questions and string matching for refusals are a smoke test, not a benchmark. Proper evaluation would add labelled answers, human review of a sample, and many more questions. Say that out loud before someone else does.

Precision versus coverage

Think of two numbers: how often the answers you do give are trustworthy, and how often you give an answer at all. Hardening raises the first and lowers the second. A bigger model (llama3.2:3b) follows instructions better, so more of its drafts survive verification, at the cost of slower CPU inference and more RAM.

Interview drill

Answer each question out loud or in writing before opening the model answer. Then message me "Drill me on Module 8" and I'll ask them in a different order, with follow-ups.

1. If RAG puts real documents in the prompt, why does it still hallucinate?
Retrieval gives the model the right material but doesn't force it to use only that material. The model also has everything it learned in training, and small models especially fill gaps with plausible-sounding recall. In this project, plain /ask retrieved two papers and cited two different, unretrieved IDs.
2. Walk me through every safeguard a question passes in your hardened agent.
Guardrail (fails closed if it has no result) → retrieval → each chunk graded separately, failures excluded → generation from relevant chunks only, or a fixed refusal with no LLM call if none → verify: strip unretrieved arXiv IDs, reject unknown "et al." authors, then an LLM groundedness check, and withhold the answer (listing the source URLs) if any check fails.
3. Why run deterministic checks before an LLM judge?
They're instant, free, repeatable, and can't be persuaded. An LLM judge is slow, costs a call, and can be wrong: this week it passed an answer citing invented authors. So code handles what code can verify exactly (IDs, author names), and the judge handles meaning. If a cheap check fails, you skip the expensive one entirely.
4. What does "fail closed" mean? Give three places you applied it.
When a safety check itself errors, choose the safe outcome. A chunk whose grading throws is excluded (the original admitted it if it had more than 50 characters); a failed groundedness check withholds the answer; a missing guardrail result routes to out_of_scope (the original continued).
5. What is response_format="content_and_artifact" and why did you need it?
The tool returns a tuple: text for the LLM and a Python object for the code. ToolNode stores them as ToolMessage.content and .artifact. Without it, documents were flattened to a string, so the grader couldn't grade per chunk and the service couldn't list sources. Caveat: the artifact only appears when the tool is invoked with a full tool call, which is why the tests invoke it that way.
6. Why grade chunks individually instead of all at once?
With one verdict for the whole context, a single relevant chunk admits the irrelevant ones, and they all reach the answer prompt as material to misuse. Per-chunk grading gives a verdict per paper, lets you generate from survivors only, gives a real chunks_used, and gives a sources list. Cost: one LLM call per chunk instead of one in total.
7. You grade with asyncio.gather. What happens if one grading call raises?
By default gather propagates the first exception and the node would crash. Here each call is wrapped in _grade_document, which catches the exception and returns a "not relevant" result, so the others still count. Results come back in argument order, which is what makes zip(documents, results) correct.
8. How does strip_unverified_citations work, and what are its limits?
A regex finds arXiv IDs (optional prefix and version); any ID not in the version-less set of retrieved IDs is deleted and recorded, then empty brackets and stray separators are tidied. Limits: it only understands arXiv-ID citations, it may match look-alike numbers, and it checks that a cited paper was retrieved, not that the paper says what the sentence claims. That last part is the groundedness check's job.
9. Why does the author check withhold the whole answer instead of deleting the bad citation?
An arXiv ID in brackets can be removed and the sentence still reads. "Rasmussen et al. showed X" is a claim built around a fake source; deleting the name leaves a claim with no support. Withholding and listing the real papers is safer than editing prose you can't trust.
10. How do you handle citation checking in a streaming endpoint?
You can't check a citation until the answer is complete, and the pieces have already been sent. So the final done event carries the cleaned answer and removed_citations, the client should replace its text with it, and only the cleaned version is cached. Alternatives: buffer the whole answer (loses streaming) or buffer sentence by sentence (complex). It's a real trade-off.
11. How do you unit-test LangGraph nodes that call an LLM?
Mock the Ollama client. The llm_returns fixture sets an AsyncMock with a list of side_effect responses on both llm.ainvoke and llm.with_structured_output(...).ainvoke; exceptions in the list are raised. Tests can then assert on routing, on the exact prompt (invoke.call_args), and that no LLM call happened (assert_not_called). This tests my logic, not the model's judgement.
12. What did you measure, and what got worse?
An eval script sends three in-scope and two out-of-scope questions to both endpoints and reports in-scope answered, out-of-scope refused, fabricated citations removed, and average latency. The agent refuses out-of-scope questions and removes fake citations, but with llama3.2:1b it also refuses many in-scope questions, and each answer takes one more LLM call. A 3B model answers more but is slower on CPU. Five questions is a smoke test, not a benchmark.
13. Name two bugs you fixed that weren't hallucinations.
The agentic router ignored the requested model (it never passed request.model to ask()), and it reported chunks_used = top_k and never returned rewritten_query. The response now reports real values and PDF URLs as sources.
