Day 1Caching concepts and the cache client

1. Why this matters

Your /ask costs 2–4 minutes of CPU. People ask the same questions again: you testing, a demo, a Telegram user pressing a button twice. A cache stores the finished answer, so an identical question is answered in milliseconds without touching OpenSearch, Jina, or Ollama. It's the cheapest performance win in the whole system, and it has a real failure mode that you hit this week.

2. Concepts

TermMeaning
Cache hit / missHit: the answer was stored, return it. Miss: compute it, then store it.
Cache keyThe name the answer is stored under. Two requests that should share an answer must produce the same key; requests that shouldn't must produce different keys.
Exact-match cacheThe key is built from the exact request. "What is RAG?" and "what is RAG?" are different keys. A semantic cache would compare meanings with embeddings instead; more hits, but risk of returning the answer to a subtly different question.
Hash (SHA-256)A function that turns any text into a fixed-length fingerprint. Same input, same fingerprint; any change, a completely different one. Used here to make short keys from long requests.
TTL (time to live)How long an entry survives before Redis deletes it automatically. Here 6 hours.
Eviction and LRUWhen Redis reaches its memory limit, it must delete something. allkeys-lru deletes the least recently used key first.
InvalidationRemoving entries that are no longer correct. "There are only two hard things in computer science: cache invalidation and naming things."
Graceful fallbackIf the cache is broken, behave as if every lookup is a miss. The cache must make the system faster, never make it fail.

src/services/cache/client.py · the whole cache in 75 lines

class CacheClient:
    def __init__(self, redis_client: redis.Redis, settings: RedisSettings):
        self.redis = redis_client
        self.settings = settings
        self.ttl = timedelta(hours=settings.ttl_hours)
 Receives a ready Redis connection instead of creating one. That's dependency injection again, and it's what lets tests pass in a fake.
    def _generate_cache_key(self, request: AskRequest) -> str:
        key_data = {
            "query": request.query,
            "model": request.model,
            "top_k": request.top_k,
            "use_hybrid": request.use_hybrid,
            "categories": sorted(request.categories) if request.categories else [],
        }
 Every field that changes the answer goes into the key. Categories are sorted so ["cs.LG","cs.AI"] and ["cs.AI","cs.LG"] share an entry. What's not in the key matters too: the prompt text and the code version (see the incident on Day 2).
        key_string = json.dumps(key_data, sort_keys=True)
        key_hash = hashlib.sha256(key_string.encode()).hexdigest()[:16]
        return f"exact_cache:{key_hash}"
 sort_keys=True makes the JSON text identical regardless of dictionary order. SHA-256 gives 64 hex characters; the first 16 are kept. The prefix groups these keys so you can find them with --scan --pattern "exact_cache:*".
    async def find_cached_response(self, request: AskRequest) -> Optional[AskResponse]:
        try:
            cache_key = self._generate_cache_key(request)
            cached_response = self.redis.get(cache_key)

            if cached_response:
                try:
                    response_data = json.loads(cached_response)
                    logger.info(f"Cache hit for exact query match")
                    return AskResponse(**response_data)
                except json.JSONDecodeError as e:
                    logger.warning(f"Failed to deserialize cached response: {e}")
                    return None

            return None

        except Exception as e:
            logger.error(f"Error checking cache: {e}")
            return None
 A hit is turned back into an AskResponse. Every failure path returns None, meaning "treat as a miss": that's the graceful fallback. Note that self.redis.get is a synchronous call inside an async def; Redis answers in well under a millisecond locally so it's harmless here, but it's the same event-loop trap as Module 0's hybrid_search. redis.asyncio would fix it.
    async def store_response(self, request: AskRequest, response: AskResponse) -> bool:
        try:
            cache_key = self._generate_cache_key(request)
            success = self.redis.set(cache_key, response.model_dump_json(), ex=self.ttl)
            if success:
                logger.info(f"Stored response in exact cache with key {cache_key[:16]}...")
                return True
            else:
                logger.warning(f"Failed to store response in cache")
                return False
        except Exception as e:
            logger.error(f"Error storing in cache: {e}")
            return False
 Stores the answer as JSON with an expiry. ex= accepts a timedelta. Failures return False and never raise.

src/services/cache/factory.py

def make_redis_client(settings: Settings) -> redis.Redis:
    redis_settings = settings.redis
    try:
        client = redis.Redis(
            host=redis_settings.host,
            port=redis_settings.port,
            password=redis_settings.password if redis_settings.password else None,
            db=redis_settings.db,
            decode_responses=redis_settings.decode_responses,
            socket_timeout=redis_settings.socket_timeout,
            socket_connect_timeout=redis_settings.socket_connect_timeout,
            retry_on_timeout=True,
            retry_on_error=[redis.ConnectionError, redis.TimeoutError],
        )
        client.ping()
        logger.info(f"Connected to Redis at {redis_settings.host}:{redis_settings.port}")
        return client
    except redis.ConnectionError as e:
        logger.error(f"Failed to connect to Redis: {e}")
        raise
    ...

def make_cache_client(settings: Settings) -> CacheClient:
    try:
        redis_client = make_redis_client(settings)
        cache_client = CacheClient(redis_client, settings.redis)
        logger.info("Exact match cache client created successfully")
        return cache_client
    except Exception as e:
        logger.error(f"Failed to create cache client: {e}")
        raise

client.ping() tests the connection at startup. Note the asymmetry: the client never raises during requests, but the factory re-raises. Since the lifespan calls it without a try, the API refuses to start if Redis is down at startup, yet keeps running if Redis dies later. You'll see both on Day 2.

Day 2Caching /ask and /stream, and measuring it

1. Why this matters

A cache client alone does nothing; it has to sit in the request path at the right places. Put it in the wrong place and you cache errors, cache "no results" forever, or skip the cache for streaming users. And once answers are cached, a bug fix doesn't reach users until the old answers expire.

2. Concepts

  • Cache-aside: the endpoint checks the cache first; on a miss it does the work and then stores the result. The cache never calls the backend itself.
  • What not to cache: errors (they may be temporary) and empty results (the papers may be indexed an hour later).
  • Replaying a cached answer as a stream: the client expects SSE events, so a cached answer is re-sent in the same event shapes, word by word.
  • Stale entries: an entry that's still within its TTL but no longer what the current code would produce.

/ask and /stream share one cache, because the key is built from the same AskRequest. Ask a question on /stream and the identical /ask is instant, and vice versa. A replayed answer is split on whitespace and re-sent with a space after each word, so line breaks in the original answer are lost. full_response must be non-empty to be stored, so a stream that failed before any text arrived isn't cached.

What happened here this week: the stale answer Before the hallucination hardening, plain /ask produced an answer citing papers that were never retrieved, and that answer was stored in Redis. After the hardening was deployed, the same question still returned the bad answer, instantly, because the cache key contains the question, model, top_k, hybrid flag and categories, but not the prompt or the code version. New code, same key, old answer, for up to 6 hours. The fix was to flush the cache. Better designs: add a version string to key_data and bump it on every change to prompts or answer logic, or flush exact_cache:* as part of each deploy.

Day 3Observability with Langfuse

1. Why this matters

When an answer is wrong or slow, "it took 3 minutes and said something odd" isn't enough to act on. Was the search bad? Was the prompt too long? Did the model ignore the passages? Tracing records every step of every request (inputs, outputs, timings) so you can open one request and see exactly where the time went and what the model was given. For LLM apps this matters more than usual, because the same code can give a different answer every time.

2. Concepts

TermMeaning
TraceThe record of one whole request, e.g. one /ask call.
SpanOne timed step inside a trace, with an input, an output, a start and an end. Spans can nest: rag_request contains search_retrieval.
GenerationA span specifically for an LLM call, with the model name, prompt, completion, and token counts.
FlushTracing libraries buffer events and send them in batches in the background, so tracing doesn't slow requests down. Flushing sends whatever is still buffered.
OpenTelemetryThe industry-standard format for traces. Langfuse v3's Python SDK is built on it; that's why the reference logs mention an "OTEL tracer provider".

Langfuse v3 is six services

ServiceJob
langfuse-webThe UI and the API that receives traces (reference port 3001, container port 3000).
langfuse-workerProcesses incoming events in the background.
langfuse-postgresUsers, projects, API keys.
clickhouseA column-oriented database for fast analytics over millions of traces.
langfuse-redisA queue between web and worker.
langfuse-minioS3-compatible object storage for raw event payloads.

class LangfuseTracer:
    def __init__(self, settings: Settings):
        self.settings = settings.langfuse
        self.client: Optional[Langfuse] = None

        if self.settings.enabled and self.settings.public_key and self.settings.secret_key:
            try:
                self.client = Langfuse(
                    public_key=self.settings.public_key,
                    secret_key=self.settings.secret_key,
                    host=self.settings.host,
                    flush_at=self.settings.flush_at,
                    flush_interval=self.settings.flush_interval,
                    debug=self.settings.debug,
                )
                logger.info(f"Langfuse v3 tracing initialized (host: {self.settings.host})")
            except Exception as e:
                logger.error(f"Failed to initialize Langfuse: {e}")
                self.client = None
        else:
            logger.info("Langfuse tracing disabled or missing credentials")

self.client is either a real Langfuse client or None. Every other method starts with "if there's no client, do nothing". That's the key design idea: tracing is optional and must never break a request. enabled defaults to True, but with empty keys the client stays None, which is why tracing was quietly off while the single-underscore variables were being ignored.

    def create_span(self, trace=None, name: str = "span", input_data: Optional[Any] = None):
        if not self.client:
            return None

        try:
            if trace is not None and hasattr(trace, "start_span"):
                return trace.start_span(name=name, input=input_data)
            return self.client.start_span(name=name, input=input_data)
        except Exception as e:
            logger.error(f"Error creating span '{name}': {e}")
            return None
 Not a context manager: the caller decides when to end it. With a parent, the new span nests under it; without, it becomes a top-level span. Note the signature has no metadata parameter. Keep that in mind for the debugging exercise.
    def end_span(self, span, output: Optional[Any] = None, metadata: Optional[Dict[str, Any]] = None, **kwargs):
        if not span:
            return

        try:
            if output is not None or metadata or kwargs:
                span.update(output=output, metadata=metadata or {}, **kwargs)

src/services/langfuse/client.py · original update_span, flush, shutdown

    def update_span(
        self,
        span,
        output: Optional[Any] = None,
        metadata: Optional[Dict[str, Any]] = None,
        level: Optional[str] = None,
        status_message: Optional[str] = None,
    ):
        if not span:
            return

        try:
            update_data = {}
            if output is not None:
                update_data["output"] = output
            if metadata:
                update_data["metadata"] = metadata
            if level:
                update_data["level"] = level
            if status_message:
                update_data["status_message"] = status_message

            if update_data:
                span.update(**update_data)
            span.end()
        except Exception as e:
            logger.error(f"Error updating span: {e}")

    def flush(self):
        """Flush any pending traces."""
        if self.client:
            try:
                self.client.flush()
            except Exception as e:
                logger.error(f"Error flushing Langfuse: {e}")

update_span also ends the span. RAGTracer.trace_search ends it again in its finally, so spans get ended twice; the second call is ignored. shutdown() flushes and calls self.client.shutdown(). Interview drill

Answer each question out loud or in writing before opening the model answer. Then message me "Drill me on Module 6" and I'll ask them in a different order, with follow-ups.

1. How does your cache decide two requests are the same?
It builds a dictionary of every request field that affects the answer (query, model, top_k, use_hybrid, sorted categories), serialises it with json.dumps(sort_keys=True), hashes it with SHA-256, and uses exact_cache: plus the first 16 hex characters as the Redis key. Same fields, same key.
2. What speedup did you measure, and why is it so large?
(Give your own numbers.) A few minutes versus well under a second. A miss runs an embedding call, a search, and minutes of CPU inference; a hit is one Redis GET of a small JSON string plus Pydantic parsing.
3. Exact-match versus semantic caching: trade-offs?
Exact: simple, never returns an answer to a different question, but misses on any rewording, even a trailing space. Semantic: embed the question and reuse an answer when similarity is above a threshold; many more hits, but it costs an embedding per request and risks answering "RAG in 2023" with the "RAG in 2020" answer. Threshold tuning and evaluation are the hard part.
4. Tell me about the stale cache incident.
An answer with fabricated citations was cached before we added citation checks. After deploying the fix, the same question still returned the bad answer, because the key doesn't include the prompt or code version and the TTL is 6 hours. We flushed Redis. Prevention: a version component in the key, bumped on prompt or logic changes, or flushing exact_cache:* on deploy. Lesson: caches store the behaviour of old code.
5. What happens if Redis goes down?
During requests: the client catches the error and treats it as a miss, and store failures return False, so answers are just slower. At startup: make_cache_client pings and re-raises, and the lifespan doesn't catch it, so the API won't start. I'd catch it in the lifespan and leave cache_client unset; get_cache_client already returns None when it's missing.
6. What is and isn't cached, and why?
Successful answers from /ask and completed /stream answers (non-empty). Not cached: errors (they raise before the store step) and "no relevant information" responses (they return early), because both might be different a minute or a day later.
7. What do TTL and allkeys-lru each protect against?
TTL bounds how long any entry, including a wrong one, can live (6 hours). maxmemory 256mb with allkeys-lru bounds memory: when full, Redis evicts the least recently used keys, so popular answers stay and the cache can't take down the host.
8. Is there a performance issue in the cache client code?
It uses the synchronous redis client inside async def methods, so each GET/SET blocks the event loop. Locally that's sub-millisecond, but with a remote Redis under load it would stall every concurrent request. Use redis.asyncio and await the calls.
9. What's a trace, a span, and a generation? Why do LLM apps need tracing more than most?
A trace is one request; spans are its timed steps with inputs and outputs, possibly nested; a generation is a span for an LLM call with model, prompt, completion and tokens. LLM output is non-deterministic and failures are "plausible but wrong" rather than exceptions, so you need the exact prompt, retrieved passages and timings of the specific bad request to debug it.
10. How do you make sure tracing can never break a request?
The tracer holds client = None when disabled or misconfigured, and every method returns early or yields None in that case; every call to Langfuse is wrapped in try/except with logging; events are sent in the background by the SDK. The original code violated this: the tracer called a method that didn't exist, so every /ask failed even with tracing off, and a test accepting 500 hid it.
11. Explain the warning create_span() got an unexpected keyword argument 'metadata', and why traces still appeared.
The agent nodes call create_span(..., metadata=...) but the method didn't accept metadata, so each call raised TypeError, which the node caught and logged, and the node's manual span was lost. The traces came from LangChain's CallbackHandler, which traces LLM calls and graph steps automatically. Fix: add a metadata parameter and forward it. A signature mismatch between caller and callee is exactly what a unit test on the tracer catches.
12. Why is Langfuse v3 six services? Would you self-host it?
Web UI/API and a worker, with Postgres for users and keys, ClickHouse for fast analytics over many traces, Redis as a queue, and S3-compatible storage for raw events. That's built for scale. For a small team I'd use the hosted version or share one instance; self-host when data can't leave the network. We also hit an image-pull 401 on MinIO and had to substitute an S3-compatible replacement.
13. What did you learn from reading a real trace?
(Answer from your own trace.) Typically: llm_generation is almost all of the time, embedding and search take well under a second, and the prompt is several thousand characters, so the optimisation targets are the model and prompt size, not the search. And you can check any cited arXiv ID against search_retrieval's output.
