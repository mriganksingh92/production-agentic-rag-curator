Day 1How search engines work, and OpenSearch in your stack

1. Why this matters

RAG is only as good as its retrieval. If the right passage never reaches the language model, no prompt can fix the answer. Postgres can do WHERE abstract LIKE '%transformer%', but that scans every row, can't tell a passage that mentions "transformer" once from one that is about transformers, and misses "Transformers" and "transform". A search engine solves all three: it's fast, it ranks, and it understands word forms.

2. Concepts

TermMeaning
DocumentOne JSON object stored in the search engine. In this project, one document = one chunk (a passage of a paper), not one paper.
IndexA named collection of documents with a shared schema, like a table. Yours will be arxiv-papers-chunks.
MappingThe index schema: which fields exist and what type each is (text, keyword, date, ...).
Inverted indexA lookup table from each word to the list of documents containing it, like the index at the back of a book. Searching "attention" reads one list instead of scanning every document.
AnalyzerThe recipe that turns text into the words (called tokens or terms) stored in the inverted index: split into words, lowercase, drop filler words, reduce to a stem.
Relevance scoreA number saying how well a document matches a query. Results are sorted by it. BM25 (Day 3) computes it.
Shard / replicaAn index is split into shards (pieces) that can live on different machines; a replica is a copy of a shard for safety. On one laptop: 1 shard, 0 replicas.

Analysis, by example

The reference index defines an analyzer called text_analyzer. This is what it does to a real title (from the reference OpenSearch, via the _analyze API):

"Retrieval-Augmented Generation for LLMs"
  tokenizer "standard"   -> Retrieval | Augmented | Generation | for | LLMs
  filter "lowercase"     -> retrieval | augmented | generation | for | llms
  filter "stop"          -> retrieval | augmented | generation | llms        ("for" removed)
  filter "snowball"      -> retriev   | augment   | generat    | llms         (stems)

The same analyzer runs on the query. So a user typing "generating retrievals" produces generat and retriev, which match. That is the whole trick behind "understands word forms". A keyword field is not analyzed at all: it stores the exact string, which is right for IDs and categories like cs.AI.

OpenSearch and Dashboards

OpenSearch is an open-source search engine (a fork of Elasticsearch), written in Java, that you talk to over HTTP with JSON. OpenSearch Dashboards is its web UI; the part you'll use is Dev Tools, a console for sending requests by hand. Java programs reserve a fixed block of memory called the heap; -Xms512m -Xmx512m sets it to 512 MB at start and maximum.

src/config.py · OpenSearchSettings

class OpenSearchSettings(BaseConfigSettings):
    model_config = SettingsConfigDict(
        env_file=[".env", str(ENV_FILE_PATH)],
        env_prefix="OPENSEARCH__",
        extra="ignore",
        frozen=True,
        case_sensitive=False,
    )

    host: str = "http://localhost:9200"
    index_name: str = "arxiv-papers"
    chunk_index_suffix: str = "chunks"  # Creates single hybrid index: {index_name}-{suffix}
    max_text_size: int = 1000000

    vector_dimension: int = 1024  # Jina embeddings dimension
    vector_space_type: str = "cosinesimil"  # cosinesimil, l2, innerproduct

Day 2The chunk index mapping and the OpenSearch client

1. Why this matters

The mapping is a contract between everything that writes to the index (your indexer, Airflow) and everything that reads it (the API, the agent). Get a field type wrong and searches silently miss, or indexing fails in the middle of the night. The client class wraps every OpenSearch call the rest of the app makes, so you only have to get them right once.

2. Concepts

Field typeStored asUse for
textAnalyzed tokens in the inverted indexFull-text search: chunk_text, title, abstract
keywordThe exact stringIDs, categories, filters, sorting: arxiv_id, categories
integer, dateNumbersRanges and sorting: chunk_index, published_date
knn_vectorA list of numbers, in a vector search structureMeaning-based search (Module 4)

A multi-field stores one value two ways: title as text for searching, and title.keyword as keyword for exact matching or sorting. Dynamic mapping is what OpenSearch does when a document contains an unknown field: by default it guesses a type and adds it. "dynamic": "strict" turns that off, so an unknown field is an error. A bulk request sends many documents in one HTTP call, which is far faster than one call per document. A refresh makes newly indexed documents visible to search; OpenSearch does it every second by default.

3. Walkthrough: real code

src/services/opensearch/index_config_hybrid.py · settings part of ARXIV_PAPERS_CHUNKS_MAPPING

ARXIV_PAPERS_CHUNKS_INDEX = "arxiv-papers-chunks"
 The name, also built from settings in the client. Only the settings version is used.
    "settings": {
        "number_of_shards": 1,
        "number_of_replicas": 0,
 One piece, no copies. A replica on a one-node cluster could never be placed anywhere, so the index would stay "yellow".
        "index.knn": True,
        "index.knn.space_type": "cosinesimil",
 Turns on vector search for this index. You won't use it until Module 4, but it must be set when the index is created; you can't switch it on later.
        "analysis": {
            "analyzer": {
                "standard_analyzer": {"type": "standard", "stopwords": "_english_"},
                "text_analyzer": {"type": "custom", "tokenizer": "standard", "filter": ["lowercase", "stop", "snowball"]},
 Two named analyzers. standard_analyzer splits and lowercases and drops English stopwords but doesn't stem: right for author names ("Park" must not become "par"). text_analyzer adds stemming: right for prose.

src/services/opensearch/index_config_hybrid.py · the fields

    "mappings": {
        "dynamic": "strict",
 Unknown fields are rejected. A typo like chunk_txt fails loudly instead of creating a useless new field.
            "chunk_id": {"type": "keyword"},
            "arxiv_id": {"type": "keyword"},
            "paper_id": {"type": "keyword"},
            "chunk_index": {"type": "integer"},
 Identity. arxiv_id is a keyword so {"term": {"arxiv_id": ...}} matches exactly. paper_id is the Postgres UUID. chunk_index is the chunk's position in its paper. (chunk_id is declared but the indexer never fills it; the client uses OpenSearch's own _id instead.)
            "chunk_text": {
                "type": "text",
                "analyzer": "text_analyzer",
                "fields": {"keyword": {"type": "keyword", "ignore_above": 256}},
            },
 The passage itself: the most important searchable field. The .keyword copy is skipped for strings over 256 characters, which is nearly every chunk, so it's rarely useful here.
            "chunk_word_count": {"type": "integer"},
            "start_char": {"type": "integer"},
            "end_char": {"type": "integer"},
 Where the chunk came from, for debugging chunking (Module 4).
            "embedding": {
                "type": "knn_vector",
                "dimension": 1024,  # Jina v3 embeddings dimension
                "method": {
                    "name": "hnsw",
                    "space_type": "cosinesimil",
                    "engine": "nmslib",
                    ...
 A slot for the chunk's meaning as 1024 numbers. Empty in this module: your stepping-stone indexer sends None, and OpenSearch simply stores no vector. Module 4 explains every line here and fills it.
            "title": {"type": "text", "analyzer": "text_analyzer", "fields": {"keyword": ...}},
            "authors": {"type": "text", "analyzer": "standard_analyzer", "fields": {"keyword": ...}},
            "abstract": {"type": "text", "analyzer": "text_analyzer"},
 The paper's metadata, copied into every chunk. This is called denormalization: storing the same data in many places so a search never has to join with Postgres. Note authors is one text string, not a list.
            "categories": {"type": "keyword"},
            "published_date": {"type": "date"},
            "section_title": {"type": "keyword"},
            "embedding_model": {"type": "keyword"},
            "created_at": {"type": "date"},
            "updated_at": {"type": "date"},
 Filters and sorting. A keyword field accepts a list, so ["cs.AI", "cs.LG"] is fine. There is no pdf_url: with strict mapping, sending one would fail, which is why search results always show "pdf_url": null.

You can see this exact mapping on the reference index with GET arxiv-papers-chunks/_mapping in the reference Dashboards (localhost:5601).

src/services/opensearch/client.py · construction and health

class OpenSearchClient:
    def __init__(self, host: str, settings: Settings):
        self.host = host
        self.settings = settings
        self.index_name = f"{settings.opensearch.index_name}-{settings.opensearch.chunk_index_suffix}"
 Our wrapper. The index name comes from settings, which is how your tests will point at a throwaway index.
        self.client = OpenSearch(
            hosts=[host],
            use_ssl=False,
            verify_certs=False,
            ssl_show_warn=False,
        )
 The low-level client from opensearch-py. Creating it doesn't connect; the first request does. Our class keeps it in self.client, which is also what tests replace with a mock.
    def health_check(self) -> bool:
        try:
            health = self.client.cluster.health()
            return health["status"] in ["green", "yellow"]
        except Exception as e:
            logger.error(f"Health check failed: {e}")
            return False
 Green: all shards placed. Yellow: data is available but some replicas aren't (normal on one node). Red: some data unavailable. Any exception, including "connection refused", becomes False: callers get a yes/no, never a crash.

src/services/opensearch/client.py · creating the index

    def setup_indices(self, force: bool = False) -> Dict[str, bool]:
        results = {}
        results["hybrid_index"] = self._create_hybrid_index(force)
        results["rrf_pipeline"] = self._create_rrf_pipeline(force)
        return results
 Called at API startup and by Airflow's setup task. Your Module 3 version has only the first line; the RRF pipeline is Module 4.
            if force and self.client.indices.exists(index=self.index_name):
                self.client.indices.delete(index=self.index_name)
 force=True means "start over": delete, then recreate. Your tests use it; production code never should.
            if not self.client.indices.exists(index=self.index_name):
                self.client.indices.create(index=self.index_name, body=ARXIV_PAPERS_CHUNKS_MAPPING)
                return True
            return False
 Idempotent: safe to call any number of times. The result is the same index, and the return value says whether this call created it.
        except Exception as e:
            # Handle race condition when multiple workers start simultaneously:
            # all check exists() -> False, all try to create, only one succeeds.
            if "resource_already_exists_exception" in str(e):
                return False
            raise
 The API container runs 4 uvicorn workers (see the CMD in the Dockerfile), each running the lifespan. Between "check" and "create", another worker can win. This handles that race; any other error is re-raised.

src/services/opensearch/client.py · bulk indexing and deleting

    def bulk_index_chunks(self, chunks: List[Dict[str, Any]]) -> Dict[str, int]:
        from opensearchpy import helpers
 Input: a list of {"chunk_data": {...}, "embedding": [...]}. The import inside the function is unusual; a top-level import would be normal.
            for chunk in chunks:
                chunk_data = chunk["chunk_data"].copy()
                chunk_data["embedding"] = chunk["embedding"]
                action = {"_index": self.index_name, "_source": chunk_data}
                actions.append(action)
 Copy first, so the caller's dictionary isn't modified. Each action says "put this document in this index". No _id is given, so OpenSearch generates a random one; indexing the same chunk twice creates a duplicate.
            success, failed = helpers.bulk(self.client, actions, refresh=True)
            return {"success": success, "failed": len(failed)}
 One HTTP request for all documents. refresh=True makes them searchable immediately (convenient; slower for huge batches). By default helpers.bulk raises BulkIndexError if any document fails, so failed is normally empty.
    def delete_paper_chunks(self, arxiv_id: str) -> bool:
            response = self.client.delete_by_query(
                index=self.index_name, body={"query": {"term": {"arxiv_id": arxiv_id}}}, refresh=True
            )
 Deletes every chunk of one paper. Because of the random IDs above, "delete then re-insert" is how this project avoids duplicates.

src/services/opensearch/factory.py

@lru_cache(maxsize=1)
def make_opensearch_client(settings: Optional[Settings] = None) -> OpenSearchClient:
    if settings is None:
        settings = get_settings()
    return OpenSearchClient(host=settings.opensearch.host, settings=settings)


def make_opensearch_client_fresh(settings: Optional[Settings] = None, host: Optional[str] = None) -> OpenSearchClient:
    ...
    opensearch_host = host or settings.opensearch.host
    return OpenSearchClient(host=opensearch_host, settings=settings)

lru_cache(maxsize=1) makes the first function a singleton: every call returns the same client (and its connection pool). The _fresh version builds a new one each time, with an optional host override; Airflow's indexing task uses it in Module 4. __init__.py re-exports OpenSearchClient, make_opensearch_client, make_opensearch_client_fresh, and QueryBuilder.

        {"chunk_data": {"arxiv_id": "1706.03762", "chunk_text": "a"}, "embedding": None},
        {"chunk_data": {"arxiv_id": "1810.04805", "chunk_text": "b"}, "embedding": None},

Day 3BM25 and the query builder

1. Why this matters

"Why did this passage rank first?" is a question you'll be asked about your own system, by users and by interviewers. Today you learn the formula OpenSearch uses, read its real calculation for one of your indexed chunks, and build the query that the API sends.

2. Concepts

From counting words to BM25

  1. Term frequency (TF): a chunk that says "retrieval" 16 times is probably more about retrieval than one that says it once.
  2. Inverse document frequency (IDF): a word that appears in every chunk ("model") tells you little; a rare word ("homomorphic") tells you a lot. IDF is high for rare words, low for common ones. TF × IDF is the classic TF-IDF score.
  3. BM25 ("Best Matching 25") fixes two weaknesses of TF-IDF. Saturation: the 16th "retrieval" should add much less than the 2nd; parameter k1 (default 1.2) controls how fast TF levels off. Length normalisation: a long chunk mentions everything more often just by being long; parameter b (default 0.75) scales TF down for chunks longer than average.

For one query word in one document, OpenSearch computes:

score = boost × idf × tf
idf   = log(1 + (N - n + 0.5) / (n + 0.5))           N = documents, n = documents containing the word
tf    = freq / (freq + k1 × (1 - b + b × dl / avgdl))   dl = this field's length, avgdl = average length

A multi-word query adds up the scores of its words. Here is OpenSearch's own explanation for one chunk in the reference index, for the word "retrieval":

3.5411  weight(chunk_text:retriev in 235), result of:
  3.5411  score(freq=16.0), computed as boost * idf * tf from:
    2.2     boost
    1.7003  idf, computed as log(1 + (N - n + 0.5) / (n + 0.5)) from:
      236     n, number of documents containing term
      1294    N, total number of documents with field
    0.9466  tf, computed as freq / (freq + k1 * (1 - b + b * dl / avgdl)) from:
      16.0    freq, occurrences of term within document
      1.2     k1, term saturation parameter
      0.75    b, length normalization parameter
      280.0   dl, length of field (approximate)
      418.5958 avgdl, average length of field

Read it top-down: the stem is retriev (the analyzer ran). 236 of 1,294 chunks contain it, so the IDF is moderate. The chunk says it 16 times and is shorter than average, so TF is close to its ceiling of 1. The boost of 2.2 is k1 + 1, a constant Lucene (the library inside OpenSearch) folds in. Scores are only comparable within one query; a BM25 score of 25 isn't "better" than 5 from a different query.

Query vocabulary

PieceMeaning
multi_matchRun one text query against several fields. "title^2" means matches in title count double.
best_fieldsA document's score is its best-matching field's score, not the sum.
operator: orA document needs any query word, not all. More results; ranking sorts them.
fuzziness: AUTOTolerate typos: 0 edits for words of 1–2 characters, 1 for 3–5, 2 for longer. prefix_length: 2 means the first 2 characters must be right, which keeps it fast.
bool with must / filtermust clauses affect the score. filter clauses only include or exclude, don't score, and are cached. Categories are a filter.
from / sizePagination: skip from results, return size.
highlightReturn snippets with the matched words wrapped in tags, here <mark>...</mark>.

Interview drill

Answer each question out loud or in writing before opening the model answer. Then message me "Drill me on Module 3" and I'll ask them in a different order, with follow-ups.

1. What is an inverted index, and why is it faster than LIKE '%word%'?
A map from each term to the list of documents containing it, built at indexing time. A query looks up a few lists and intersects or merges them, instead of scanning every row's text. LIKE with a leading wildcard can't use a normal database index, so it reads everything, and it has no notion of relevance or word forms.
2. What does an analyzer do? Why are there two in this project?
It turns text into terms: tokenize, lowercase, remove stopwords, stem. It runs on documents at index time and on queries at search time, so both sides match. text_analyzer stems, for prose (retrieval and retrieving both become retriev). standard_analyzer doesn't stem, for author names, where stemming would mangle them.
3. text vs keyword: which for arxiv_id, categories, chunk_text, and why?
keyword stores the exact string: IDs and categories, used in exact filters (term, terms) and sorting. text is analyzed for full-text search: chunk_text. A keyword filter is case-sensitive and matches only the whole value.
4. Explain BM25 without the formula, then name its two parameters.
A document scores higher when it contains the query's words, especially rare ones (IDF), and more often (TF), but repeated occurrences add less and less (saturation, k1 = 1.2), and long documents are penalised for mentioning things just by being long (length normalisation, b = 0.75). Scores for multiple words add up. I read a real explanation in our index: idf 1.70 for "retrieval" (236 of 1,294 chunks), tf 0.95.
5. Why is the mapping "dynamic": "strict"? What's the cost?
Unknown fields fail loudly instead of silently creating new, possibly wrongly typed fields; a typo can't pollute the index. The cost: every writer must match the schema exactly, and adding a field means changing the mapping. For example, a pdf_url field is rejected, which is why hits have pdf_url: null.
6. Why does every chunk store the paper's title, authors, and abstract?
Denormalization. A search engine has no joins, so to filter by category, show the title, or boost title matches without a second lookup in Postgres, each chunk carries the paper's metadata. Trade-off: more storage, and updating a paper means reindexing all its chunks.
7. must vs filter in a bool query?
Both must match. must contributes to the score; filter only includes or excludes, doesn't score, and can be cached. Categories are a filter because "is it cs.AI" shouldn't change how relevant a passage is.
8. What do operator: or and fuzziness: AUTO trade off?
Recall (finding everything relevant) against precision (only relevant things). or returns documents matching any word, relying on ranking to put the best first. Fuzziness tolerates typos (1–2 edits by word length) at some cost in speed and occasional false matches; prefix_length: 2 limits the cost.
9. How does the API behave when OpenSearch is down at startup, and during a request?
At startup, health_check returns False, the lifespan logs a warning and skips index setup; the API still starts. During a request the endpoint checks health first and returns 503. /health reports "degraded". One gap: if the index is missing, search_unified swallows the error and returns zero results with status 200.
10. Why does index creation handle resource_already_exists_exception?
The API runs 4 uvicorn workers, each running the lifespan. All can see "index doesn't exist" and try to create it; only one wins. A check-then-act race. Treating "already exists" as success makes setup safe to run concurrently.
11. How would you make re-indexing a paper idempotent? What does this project do?
Either give each chunk a deterministic _id (e.g. {arxiv_id}-{chunk_index}) so re-indexing overwrites, or delete the paper's chunks before inserting. The project uses random IDs plus delete_by_query on arxiv_id. Deterministic IDs would be cheaper, but wouldn't remove leftover chunks if a paper now produces fewer chunks.
12. Where would pure keyword search fail for this app?
Synonyms and paraphrases: a question about "LLMs making things up" won't match a passage that says "hallucination". It's also blind to meaning and word order. It's strong for exact terms, names, and acronyms. That's the motivation for vector search and hybrid search in Module 4.
