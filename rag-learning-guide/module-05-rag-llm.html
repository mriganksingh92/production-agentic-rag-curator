Day 1What an LLM is, and running one with Ollama

1. Why this matters

Search returns passages; a user wants an answer. A large language model (LLM) can turn five passages into three readable sentences. The course runs the model locally with Ollama instead of calling a paid API: no key, no per-question cost, and no data leaves your laptop. The price is speed. On your CPU, one answer takes minutes, and that single fact explains several bugs you'll meet in this module and the next.

2. Concepts

What an LLM does

An LLM does one thing: given some text, it predicts a likely next piece of text, adds it, and repeats. Everything else (answering, summarising, "reasoning") is that loop, steered by what you put in front of it. The words you need:

TermMeaning
TokenThe unit the model reads and writes: a word, part of a word, or punctuation. Roughly 3/4 of an English word on average. Speed and limits are measured in tokens.
PromptAll the text you send: instructions, the retrieved passages, and the question. The model only knows what is in the prompt plus what it memorised in training.
Context windowThe maximum number of tokens the model can look at at once (prompt plus answer). Too many passages and the oldest text is cut off.
TemperatureHow random the choice of the next token is. 0 = always the most likely token (repeatable). Higher = more varied, more creative, more likely to invent things.
top_pAnother randomness control: only sample from the smallest set of tokens whose probabilities add up to p.
Prompt evaluation vs. generationFirst the model reads the whole prompt (prompt evaluation), then writes the answer one token at a time (generation). Both cost time.
HallucinationConfident text that isn't supported by anything: invented facts, invented paper IDs, invented authors. RAG reduces it; it does not remove it (Module 8).

RAG in one picture

Question→ Search (Module 4)→ Top passages→ Prompt = rules + passages + question→ LLM→ Answer + sources

Ollama

Ollama is a server program that downloads open models and runs them, answering over HTTP on port 11434. The endpoints this project uses:

EndpointWhat it does
GET /api/versionReturns {"version": "0.11.2"}. Used as a health check.
GET /api/tagsLists the models you've pulled.
POST /api/generateBody {"model", "prompt", "stream"}. With "stream": false, one JSON reply. With "stream": true, one JSON object per line as tokens are produced (called NDJSON, newline-delimited JSON).

The model is llama3.2:1b: Meta's Llama 3.2 with 1.2 billion parameters, about 1.3 GB on disk. That is tiny for an LLM, which is why it fits on a laptop, and also why it makes more mistakes than big hosted models.

Real numbers from your laptop this week One call to the reference Ollama with a 37-token prompt took 46 seconds: 17.6 s loading the model into memory, 5.1 s reading the prompt (about 7 tokens per second), and 23.2 s writing 56 tokens (about 2.4 tokens per second). A RAG prompt with three passages is a few thousand tokens, so the model can spend minutes just reading before it writes its first word. That's why a real /ask takes 2–4 minutes here. A GPU would make both phases 10–100× faster.

Day 2The Ollama client

1. Why this matters

The rest of the app should call await ollama_client.generate(...) and never deal with URLs, JSON bodies, status codes, or httpx exceptions. OllamaClient is that wrapper. It's also the single place where the timeout lives, so it's where the slowness of CPU inference turns into errors, or doesn't.

2. Concepts

  • Client wrapper: a class that hides a remote service behind ordinary methods. The OpenSearch and Jina clients from Modules 3–4 follow the same pattern.
  • Exception translation: catch low-level errors (httpx.ConnectError, httpx.TimeoutException) and raise your own (OllamaConnectionError, OllamaTimeoutError).
  • httpx timeouts are per step, not per request. httpx.Timeout(300.0) sets four limits of 300 s each: connect, write, pool, and read. The read limit is the longest wait for the next piece of data. A streaming reply that sends a token every few seconds can run for ten minutes without timing out; a reply that stays silent for 301 seconds fails.
  • Async generator (Module 0, Day 2): generate_stream yields each parsed line as it arrives.
  • Mocking HTTP in tests: httpx.MockTransport(handler) makes a client call your function instead of the network. Your tests will swap it in for every httpx.AsyncClient the code creates.

        try:
            async with httpx.AsyncClient(timeout=self.timeout) as client:
                data = {"model": model, "prompt": prompt, "stream": True, **kwargs}

client.stream(...) opens the request without reading the whole body. aiter_lines() hands over one NDJSON line at a time, as Ollama writes it. Blank lines are skipped and broken lines are logged and skipped, so one bad line doesn't kill a four-minute answer. Each parsed dictionary is yielded to whoever is looping over generate_stream.

Day 3Prompts and RAG answers

1. Why this matters

The prompt is the only steering wheel you have. The same model with the same passages gives a grounded answer or an invented one depending on how the instructions and passages are laid out. Today you'll build the prompt exactly as the course does, and see its weak spots, which Module 8 fixes.

2. Concepts

  • System prompt: fixed instructions at the top (role, rules, length). Kept in a text file so you can edit it without touching code.
  • Grounding: telling the model to answer only from the supplied passages, and labelling each passage with an ID it can cite.
  • Structured output: asking the model for JSON matching a schema. Ollama supports a format field holding a JSON Schema. Pydantic can generate that schema with Model.model_json_schema().
  • Defensive parsing: small models often wrap JSON in chatter ("Here's the JSON: {...}"). The parser tries strict JSON, then a regular expression that pulls out the first {...}, then gives up and treats the whole reply as plain text.

            parsed_json = json.loads(response)

            return validated_response.model_dump()
        except (json.JSONDecodeError, ValidationError):

    @staticmethod
    def _extract_json_fallback(response: str) -> Dict[str, Any]:
        json_match = re.search(r"\{.*\}", response, re.DOTALL)
        if json_match:
            try:
                parsed = json.loads(json_match.group())
                validated = RAGResponse(**parsed)
                return validated.model_dump()
            except (json.JSONDecodeError, ValidationError):
                pass

        return {
            "answer": response,
            "sources": [],
            "confidence": "low",
            "citations": [],
        }

Day 4The /ask and /stream endpoints, and the Gradio chat UI

1. Why this matters

Today everything joins up: search, prompt, model, HTTP. You'll also meet the most user-visible design question in a slow system: do you make the user stare at a spinner for three minutes, or show the answer word by word as it's written? The course offers both, and the chat UI uses the streaming one.

2. Concepts

  • Server-Sent Events (SSE): a simple text format for pushing messages over one long HTTP response. Each message is a line data: <text> followed by a blank line. Here the text is JSON.
  • StreamingResponse: FastAPI's response type that takes a generator and sends each yielded string immediately.
  • An error mid-stream can't change the status code. The 200 OK goes out with the first byte. If something fails later, the only way to tell the client is inside the stream, which is what the {"error": ...} event is for.
  • Graceful degradation: if the embedding service fails, fall back to keyword-only search instead of failing the whole request.
  • Gradio: a Python library that builds a web UI from a few components (text box, button, markdown area) and calls your Python function when the user submits. If the function is a generator, the UI updates on every yield.

Answer each question out loud or in writing before opening the model answer. Then message me "Drill me on Module 5" and I'll ask them in a different order, with follow-ups.

1. Explain RAG in two sentences, and why you'd use it instead of just asking the LLM.
Retrieve the passages most relevant to the question, put them in the prompt, and have the model answer from them. It gives the model facts it never saw in training (papers from this week), lets you show sources, and reduces invented answers, without retraining the model.
2. What are tokens and the context window, and why do they matter for top_k?
Tokens are the word-pieces a model reads and writes; the context window is the maximum it can consider at once. Each extra passage adds hundreds of tokens: more context, but a slower answer on CPU (prompt reading here is about 7 tokens per second) and eventually truncation. top_k=3 is a speed/recall trade-off.
3. Why does one answer take 2–4 minutes on this laptop? What would you change in production?
A CPU runs the 1.2-billion-parameter model slowly: we measured 17.6 s to load it, about 7 tokens/s reading the prompt, and about 2.4 tokens/s writing. A RAG prompt is thousands of tokens. In production: a GPU, or a hosted model, a smaller prompt (fewer and shorter chunks), keeping the model loaded, streaming so users see progress, and caching repeat questions (Module 6).
4. Walk through what happens when /ask receives a question.
Pydantic validates the body (422 if invalid). If hybrid, the question is embedded with Jina; on failure it falls back to BM25. search_unified returns the top_k chunks. If none, a fixed "couldn't find" answer, with no LLM call. Otherwise the prompt builder puts the system prompt, labelled chunks, and question into one string; Ollama generates; the client adds source URLs derived from the chunks; the router returns an AskResponse. Any exception becomes a 500.
5. How does streaming work end to end, and why send metadata first?
Ollama streams NDJSON lines; generate_stream yields each parsed line; the endpoint's async generator turns each into an SSE data: {...} event; StreamingResponse sends each immediately; Gradio reads lines with aiter_lines and re-renders on every yield. Metadata goes first because retrieval is fast and generation is slow: the user sees sources while waiting.
6. If the LLM fails halfway through a stream, what status code does the client get? Why?
200. The status line goes out with the first byte, before the failure. The only way to report it is inside the stream, so the endpoint yields {"error": ...} and the client has to check for it. Monitoring that only looks at status codes will miss these failures.
7. Tell me about a production bug you debugged in this project. (The Gradio timeout.)
The chat UI said "make sure the API server is running" while health checks were green. I read the actual exception: an httpx.ReadTimeout. The client had a 60 s timeout, and on CPU Ollama took over a minute reading the prompt before the first token, so no bytes arrived for 60 s. The handler caught every RequestError and printed a misleading message. The fix was httpx.Timeout(600.0, connect=10.0): long read timeout, short connect timeout. Lessons: httpx timeouts are per operation, not total; and error messages should not guess the cause.
8. What's the difference between the read timeout and the connect timeout, and why set them differently?
Connect: how long to wait to establish the TCP connection. If the server is down, that fails fast. Read: the longest gap between received bytes. A slow but healthy LLM needs a long read timeout; a dead server should be detected in seconds, hence 10 s connect, 600 s read.
9. Does the response's citations field tell you which papers the answer used?
No. It's the list of retrieved chunk IDs, whatever the answer says, and confidence is hard-coded to "medium". The model can cite a paper that was never retrieved and nothing notices. That's exactly how this week's fabricated citations got through, and what Module 8's deterministic citation check fixes.
10. The client passes temperature=0.7. What temperature does Ollama actually use?
Its default. generate spreads extra arguments into the top level of the JSON body, but Ollama reads sampling parameters from "options" and ignores unknown top-level fields. I verified it: with top-level temperature: 0 three runs gave three different outputs; with options.temperature: 0 they were identical. Fix: send {"options": {"temperature": ..., "top_p": ...}}. For grounded QA I'd use a low temperature.
11. Why does search_mode sometimes lie?
It's computed from request.use_hybrid, not from what ran. If embedding fails, the search falls back to BM25 but the response still says "hybrid". The fix is to return "hybrid" if query_embedding is not None else "bm25". Small, but it misleads anyone debugging answer quality.
12. Why test the endpoints with a small app and dependency_overrides instead of the real app?
The real app's lifespan connects to Postgres, OpenSearch, and Ollama; tests would be slow, flaky, and need Docker. Overriding the dependency functions swaps in mocks, so each test controls exactly what search and the LLM return, including failures, and runs in milliseconds. The reference's own tests accept 200/500/503 for the same call, so they can't catch a broken endpoint.
13. Local LLM versus a hosted API like OpenAI: trade-offs?
Local: no per-call cost, no data leaves the machine, works offline, full control of the model version; but slow without a GPU, smaller models, and you operate it. Hosted: much faster and more capable, no infrastructure; but cost per token, data leaves your network, rate limits, and model versions can change under you.
