Day 1FastAPI basics

1. Why this matters

Every feature of this project, from search to the agent, is reached through one HTTP API. FastAPI is the framework that turns Python functions into HTTP endpoints. It reads your type hints and Pydantic models to validate requests, shape responses, and generate the /docs page for free. Once you can read one endpoint, you can read all of them.

2. Concepts

TermMeaning
AppThe FastAPI() object. It holds every route and is what the server runs.
Path operationOne method + path pair, like GET /api/v1/health, mapped to one Python function (the "endpoint").
RouterAn APIRouter(): a group of path operations in its own file. The app includes routers, optionally under a prefix like /api/v1.
Response modelA Pydantic model named in response_model=. FastAPI validates what you return against it and filters out extra fields.
OpenAPIA standard JSON description of an API. FastAPI builds it at /openapi.json; /docs is an interactive page drawn from it.
ASGI server (uvicorn)The program that listens on a port, receives HTTP, and calls your app. FastAPI is the app; uvicorn is the server.

FastAPI decides where each function parameter comes from by its type: a Pydantic model means "JSON body", a plain int in the path means "path parameter", and a special marker (Depends, tomorrow) means "compute it for me". Return values are converted to JSON.

Day 2Settings, lifespan, and dependency injection

1. Why this matters

Hard-coded values don't survive contact with Docker: inside a container, Postgres is at postgres:5432; on your laptop, at localhost:15432. The project solves this with three patterns you'll meet in every file: a settings class that reads the environment, a lifespan that creates expensive objects once at startup, and dependency injection that hands those objects to each endpoint.

2. Concepts

pydantic-settings, the real version

You built a small CuratorSettings in Module 0. The reference uses the same library with two more ideas: one settings class per subsystem, each with its own environment prefix (ARXIV__, OPENSEARCH__), and a top-level Settings that contains them. Values come from, in order of priority: arguments you pass, real environment variables, the .env file, then the defaults in the class.

Lifespan

A lifespan is an async context manager that FastAPI runs around the app's whole life: code before yield runs once at startup, code after it once at shutdown. It's where the API opens its database pool and creates its clients. app.state is a place to keep those objects so any request can reach them.

Dependency injection

Dependency injection means a function declares what it needs, and something else provides it. In FastAPI you write settings: Annotated[Settings, Depends(get_settings)]: "before calling me, call get_settings() and pass the result". The payoff comes in tests: app.dependency_overrides[get_settings] = fake swaps the provider without touching the endpoint. Annotated[...] just attaches extra information (the Depends) to a type. The project gives each combination a short alias, like SettingsDep.

lru_cache

@lru_cache (from functools) remembers a function's return value per argument combination. On a function with no arguments, it means "compute once, then return the same object forever": a cheap singleton.

Day 3SQL, PostgreSQL, and the database layer

1. Why this matters

Every paper the pipeline fetches (metadata, full text, sections) lands in PostgreSQL. Search indexes are rebuilt from it. When something looks wrong in search, the first question is "what's in the database?", and you answer it in SQL. Today you learn enough SQL to answer it, then the Python layer the project wraps around the database.

2. Concepts

TermMeaning
Relational databaseData in tables: rows (one paper each) and typed columns (title, date, ...). PostgreSQL is one.
Primary keyA column that uniquely identifies a row. Here, id, a UUID (a random 128-bit ID).
ConstraintA rule the database enforces: NOT NULL, UNIQUE. It protects data even from buggy code.
IndexA lookup structure that makes WHERE arxiv_id = ... fast instead of scanning every row.
TransactionA group of changes that succeed or fail together. BEGIN ... COMMIT saves; ROLLBACK undoes.
JSON columnA column holding a JSON value, used here for lists like authors and sections.

SQLAlchemy in three objects

ObjectRole
EngineKnows how to reach the database and keeps a connection pool: a set of open connections reused across requests, because opening one is slow.
SessionA unit of work: borrows a connection, tracks the objects you add or change, and writes them on commit().
sessionmakerA factory that creates sessions bound to the engine.

psycopg2 is the driver: the low-level library that speaks Postgres's network protocol. SQLAlchemy sits on top of it.

src/db/interfaces/base.py · the contract

class BaseDatabase(ABC):
    """Base class for database operations."""

    @abstractmethod
    def startup(self) -> None:
        """Initialize the database connection."""

    @abstractmethod
    def teardown(self) -> None:
        """Close the database connection."""

    @abstractmethod
    def get_session(self) -> ContextManager[Session]:
        """Get a database session."""

An abstract base class (ABC) lists methods a subclass must implement; Python refuses to create a subclass instance that's missing one. The rest of the code depends on BaseDatabase, not on Postgres, which is what lets tests pass in a fake. The same file defines a BaseRepository ABC that nothing actually inherits from; the real repository (Day 4) doesn't use it. Copy it anyway so your file matches.

src/db/interfaces/postgresql.py · the real implementation

Base = declarative_base()
 The parent class for every table model (Day 4). It also keeps Base.metadata: a registry of all tables whose model classes have been imported.
def __init__(self, config: PostgreSQLSettings):
    self.config = config
    self.engine: Optional[Engine] = None
    self.session_factory: Optional[sessionmaker] = None
 The constructor does no I/O. Connecting happens in startup(), so creating the object is cheap and safe.
self.engine = create_engine(
    self.config.database_url,
    echo=self.config.echo_sql,
    pool_size=self.config.pool_size,
    max_overflow=self.config.max_overflow,
    pool_pre_ping=True,  # Verify connections before use
)
 Create the engine and its pool. echo prints every SQL statement (great for learning). pool_pre_ping tests a pooled connection before handing it out, so a Postgres restart doesn't break the next request.
self.session_factory = sessionmaker(bind=self.engine, expire_on_commit=False)
 expire_on_commit=False: after a commit, objects keep their loaded values instead of reloading on next access. Handy when you return them after the session closes.
with self.engine.connect() as conn:
    conn.execute(text("SELECT 1"))
 Prove the connection works now, at startup. text() marks a raw SQL string.
Base.metadata.create_all(bind=self.engine)
 Create every registered table that doesn't exist yet. Idempotent: running it twice is fine. It does not alter existing tables; real projects use a migration tool (the reference lists Alembic as a dependency but doesn't use it).
except Exception as e:
    logger.error(f"Failed to initialize PostgreSQL database: {e}")
    raise
 Log and re-raise: the API must not start without its database.
@contextmanager
def get_session(self) -> Generator[Session, None, None]:
    if not self.session_factory:
        raise RuntimeError("Database not initialized. Call startup() first.")
    session = self.session_factory()
    try:
        yield session
    except Exception:
        session.rollback()
        raise
    finally:
        session.close()
 The core pattern. Hand out a session; if the block raises, undo uncommitted changes; always return the connection to the pool. This is exactly the context manager from Module 0, Day 2.

src/schemas/database/config.py and src/db/factory.py · glue

class PostgreSQLSettings(BaseSettings):
    database_url: str = Field(default="postgresql://rag_user:rag_password@localhost:5432/rag_db", ...)
    echo_sql: bool = Field(default=False, ...)
    pool_size: int = Field(default=20, ...)
    max_overflow: int = Field(default=0, ...)

    class Config:
        env_prefix = "POSTGRES_"
def make_database() -> BaseDatabase:
    settings = get_settings()
    config = PostgreSQLSettings(
        database_url=settings.postgres_database_url,
        echo_sql=settings.postgres_echo_sql,
        pool_size=settings.postgres_pool_size,
        max_overflow=settings.postgres_max_overflow,
    )
    database = PostgreSQLDatabase(config=config)
    database.startup()
    return database

The factory pattern: one function knows how to build a ready-to-use object from settings. Every service in the project has a make_... factory. Note that make_database() connects immediately. src/database.py is an older helper that keeps one global database; nothing in the reference imports it. Copy it for parity, but you won't use it.

The duplicate insert fails with duplicate key value violates unique constraint. Inside the transaction the count is 0; after ROLLBACK it's 2 again. \d (a psql command, not SQL) describes a table, including its indexes.

Day 4The Paper model and the repository

1. Why this matters

The papers table is the project's source of truth. Two pieces of code define it: a SQLAlchemy model (the table, as a Python class) and Pydantic schemas (the data crossing into and out of it). A repository is the only code allowed to run queries on it, so the rest of the project says repo.upsert(paper) instead of writing SQL.

2. Concepts

An ORM (object-relational mapper) maps a class to a table and instances to rows. You write select(Paper).where(Paper.arxiv_id == "1706.03762"); SQLAlchemy writes the SQL. The repository pattern puts all such queries behind one class with plain methods (create, get, list, update). Callers don't know or care whether the data lives in Postgres. An upsert means "update if it exists, insert if it doesn't", which makes re-running a pipeline safe.

Model versus schema src/models/paper.py (SQLAlchemy) describes storage: column types, keys, defaults. src/schemas/arxiv/paper.py (Pydantic) describes data in motion: what the pipeline hands in, what an API would return. They have almost the same fields, on purpose, for different jobs.

src/repositories/paper.py · the methods that matter

class PaperRepository:
    def __init__(self, session: Session):
        self.session = session
 A repository wraps one session. The caller owns the session's lifetime.
    def create(self, paper: PaperCreate) -> Paper:
        db_paper = Paper(**paper.model_dump())
        self.session.add(db_paper)
        self.session.commit()
        self.session.refresh(db_paper)
        return db_paper
 Pydantic to dict to model. add stages the row; commit writes it; refresh reloads it so database-filled values are present.
    def get_by_arxiv_id(self, arxiv_id: str) -> Optional[Paper]:
        stmt = select(Paper).where(Paper.arxiv_id == arxiv_id)
        return self.session.scalar(stmt)
 Paper.arxiv_id == arxiv_id doesn't compare now; it builds a SQL condition. scalar returns the first result or None.
    def get_all(self, limit: int = 100, offset: int = 0) -> List[Paper]:
        stmt = select(Paper).order_by(Paper.published_date.desc()).limit(limit).offset(offset)
        return list(self.session.scalars(stmt))
 Newest first, with pagination: limit rows, skipping offset. scalars yields model objects.
    def get_count(self) -> int:
        stmt = select(func.count(Paper.id))
        return self.session.scalar(stmt) or 0
 SELECT count(papers.id) FROM papers.
    def upsert(self, paper_create: PaperCreate) -> Paper:
        existing_paper = self.get_by_arxiv_id(paper_create.arxiv_id)
        if existing_paper:
            for key, value in paper_create.model_dump(exclude_unset=True).items():
                setattr(existing_paper, key, value)
            return self.update(existing_paper)
        else:
            return self.create(paper_create)
 Read, then write. exclude_unset=True copies only fields the caller actually set, so a metadata-only update doesn't wipe parsed text. Interview point: two processes upserting the same ID at once can race; Postgres's INSERT ... ON CONFLICT does it atomically.

The other methods (get_by_id, get_processed_papers, get_unprocessed_papers, get_papers_with_raw_text, get_processing_stats, update) follow the same shapes. Read them in the reference.

Who creates the papers table? create_all creates tables for models that have been imported. The reference API never imports src.models.paper, so the API's startup creates no tables. The table is created by Airflow (Module 2), whose task code imports the metadata fetcher, which imports the repository, which imports the model, before calling make_database(). Day 5The health check, exceptions, and testing with overrides

1. Why this matters

A health endpoint is how Docker, load balancers, and you decide whether the service works. A good one checks each dependency separately and reports "degraded" rather than crashing. Today you connect all the pieces: lifespan creates the database, dependency injection hands it to the endpoint, and tests swap it for a fake.

2. Concepts

Dependency chains: a dependency can itself depend on another. SessionDep calls get_db_session, which declares Depends(get_database). FastAPI resolves the chain for every request. A dependency written as a generator (with yield) gets its cleanup code run after the response, which is how a session is closed per request.

Two ways to fake things in tests. unittest.mock.patch("src.main.make_database", ...) replaces a name for the duration of a with block; you use it for code FastAPI doesn't inject, like the lifespan. app.dependency_overrides replaces an injected dependency; you use it for endpoints. Patch the name where it is looked up: src.main did from src.db.factory import make_database, so the name to patch lives in src.main.

Custom exceptions: a hierarchy like RepositoryException → PaperNotFound lets callers catch a whole family with one except, and makes logs say what failed in the project's own terms.

2. Concepts

TermMeaning
Multi-stage buildSeveral FROM lines in one Dockerfile. An early stage has the build tools; the final stage copies only the results. The shipped image stays smaller.
Build contextThe folder sent to Docker (the . in build: .). COPY can only see files inside it.
BuildKit cache mountRUN --mount=type=cache,... keeps a folder (like uv's download cache) between builds without putting it in the image.
depends_on: condition: service_healthyDon't start this service until that one's healthcheck passes. Without it, the API would start before Postgres accepts connections and crash.
CA certificateA root certificate your machine trusts. Your office proxy re-signs HTTPS traffic with the company's own CA, so containers must trust it too.

3. Walkthrough: real code

Dockerfile · the API image (working-tree version, with the proxy fix)

FROM ghcr.io/astral-sh/uv:python3.12-bookworm AS base
WORKDIR /app
COPY pyproject.toml uv.lock ./
 Stage one, named base: an image with Python 3.12 and uv. Copy only the dependency files first, so this layer's cache survives code changes.
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy
 Precompile .pyc files for faster startup; copy instead of hard-linking (the cache is on a different filesystem).
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=/app/uv.lock \
    --mount=type=bind,source=pyproject.toml,target=/app/pyproject.toml \
    uv sync --frozen --no-dev
 Install dependencies into /app/.venv. --frozen: use uv.lock exactly and fail if it's out of date. --no-dev: skip pytest and friends. The cache mount keeps downloads between builds.
COPY src /app/src
 Your code, last, because it changes most often.
FROM python:3.12.8-slim AS final
EXPOSE 8000
ENV PYTHONUNBUFFERED=1
ARG VERSION=0.1.0
ENV APP_VERSION=$VERSION
 Stage two: a slim Python image without uv. PYTHONUNBUFFERED makes logs appear immediately in docker logs. APP_VERSION feeds the version in main.py.
WORKDIR /app
COPY --from=base /app /app
ENV PATH="/app/.venv/bin:$PATH"
 Copy the finished virtual environment and code from stage one. Putting .venv/bin first on PATH makes python and uvicorn the project's.
COPY certs/corp-ca.crt /usr/local/share/ca-certificates/corp-ca.crt
RUN cat /usr/local/share/ca-certificates/corp-ca.crt >> "$(python -c 'import certifi; print(certifi.where())')"
 The proxy fix (not in the original course). httpx and requests trust the certifi bundle, not the system store, so the corporate root is appended to that file. Needed for outgoing calls to arXiv and Jina in later modules.
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4"]
 Four worker processes, each with its own lifespan, so each opens its own pool of up to 20 Postgres connections. Postgres allows 100 by default. Good interview arithmetic.

Notice the cert is only added in the final stage. The uv sync in the base stage downloads packages without it, and the reference image builds fine on this network, so package downloads aren't what the proxy breaks.

compose.yml · the reference api service (first half)

  api:
    build: .
    container_name: rag-api
    ports:
      - "8000:8000"
    depends_on:
      postgres:
        condition: service_healthy
      opensearch:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD-SHELL", "python -c \"import urllib.request; urllib.request.urlopen('http://localhost:8000/api/v1/health')\""]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
    env_file:
      - .env
    environment:
      # Container-specific overrides
      ...
      - POSTGRES_DATABASE_URL=postgresql+psycopg2://rag_user:rag_password@postgres:5432/rag_db
      ...

build: . builds the Dockerfile in this folder instead of pulling an image. The healthcheck uses Python's standard library because the slim image has no curl. env_file loads your whole .env into the container; environment then overrides specific values. Inside the container, the API reaches Postgres at postgres:5432, the internal port, not 15432.

What happened here this week The reference API image is 12.8 GB, and rebuilds took about 30 minutes: the dependency layer (torch and friends, pulled in by the PDF parser in Module 2) kept being evicted from a build cache that had hit its 30 GB limit. Your image today is small, because you only have FastAPI, SQLAlchemy, and a few libraries. Enjoy fast builds while they last.

6. Break it

  1. Remove the environment: override for POSTGRES_DATABASE_URL, and change .env to the localhost:15432 URL. Rebuild. Health is degraded with a connection-refused message: inside a container, localhost is the container itself. Revert both.
  2. Remove depends_on, then docker compose down and up -d. Watch docker compose logs api: the API may try to connect before Postgres is ready and crash at startup. Restore it.
  3. Comment out the two certificate lines in the Dockerfile and rebuild. Nothing breaks yet, because your API makes no outgoing HTTPS calls. Module 2's arXiv downloads would fail with CERTIFICATE_VERIFY_FAILED. Restore them.

Interview drill

Answer each question out loud or in writing before opening the model answer. Then message me "Drill me on Module 1" and I'll ask them in a different order, with follow-ups.

1. What does FastAPI do with a function's type hints?
It decides where each parameter comes from (path, query, body, dependency), validates incoming data with Pydantic, validates and filters the return value against response_model, and generates the OpenAPI schema and /docs page. Invalid requests get a 422 before your code runs; invalid responses raise a server error.
2. What is the lifespan, and what goes in it?
An async context manager that runs once at startup (before yield) and once at shutdown (after). It creates expensive shared objects (the database pool, service clients) and stores them on app.state; shutdown closes them, e.g. database.teardown() disposes the engine's pool.
3. Explain dependency injection in FastAPI and why it helps testing.
An endpoint declares Annotated[Type, Depends(provider)]; FastAPI calls the provider per request and passes the result. Dependencies can chain and can be generators with cleanup. In tests, app.dependency_overrides[provider] = fake swaps the provider without touching endpoint code: I test the health endpoint with a fake database that can be told to fail.
4. There are two get_settings functions in the project. What's the difference?
src.config.get_settings builds a fresh Settings() on every call; factories like make_database use it. src.dependencies.get_settings is wrapped in @lru_cache, so endpoints share one instance per process. To override settings in a test, you override the dependencies version, because that's the object FastAPI knows about.
5. In what order does pydantic-settings pick a value, and why does the API use postgres:5432 but your tests localhost:15432?
Explicit arguments, then environment variables, then the .env file, then class defaults. Inside Docker, the service name postgres resolves on the Compose network and the internal port is 5432. From the laptop that name doesn't resolve; you reach the same database through the published port 15432. That's also why 13 reference API tests fail on the host with getaddrinfo failed.
6. Engine, connection pool, session: what is each?
The engine knows the database URL and owns a pool of open connections that get reused, because opening a connection is slow. A session is a unit of work that borrows a connection, tracks added or changed objects, and writes them on commit. get_session rolls back on error and always closes the session, returning the connection.
7. What does Base.metadata.create_all do, and what are its limits?
It issues CREATE TABLE for every registered model whose table doesn't exist. Models register when their module is imported, which is why the reference API never creates papers (it never imports the model) and Airflow does. It never alters existing tables, so schema changes need a migration tool like Alembic.
8. What is the repository pattern, and what does upsert do here?
All queries for one table live in one class with plain methods, so the rest of the code never writes SQL and can be tested with a fake. upsert looks up by arxiv_id, then updates the fields the caller set (exclude_unset=True) or inserts. It makes re-running ingestion safe. It's read-then-write, so concurrent writers could race; INSERT ... ON CONFLICT would be atomic.
9. Why does the model have both unique=True and a Pydantic schema? Isn't that duplicate validation?
They protect different boundaries. Pydantic checks shape and types when data enters the code. Database constraints (NOT NULL, UNIQUE) hold even if a bug, a script, or another service bypasses the code. Duplicate arXiv IDs are prevented by the database, not by Python.
10. How do your repository tests avoid leaving rows in the database?
Each test gets a session bound to a connection with an open outer transaction, using join_transaction_mode="create_savepoint". The repository's commit() calls only release savepoints; the fixture rolls back the outer transaction at the end. Real SQL, real constraints, no leftover data.
11. Why does the health endpoint return 200 with "degraded" instead of 500 when the database is down?
The API process is alive and can report what's wrong. Each dependency check is wrapped so one failure records "unhealthy" with the error message instead of crashing. A monitor can read the body. The trade-off: a load balancer that only looks at status codes will keep sending traffic; some teams return 503 for degraded.
12. Walk me through the API Dockerfile.
Two stages. The uv stage copies pyproject.toml and uv.lock first and runs uv sync --frozen --no-dev with a cache mount, so the dependency layer is cached across code changes; then it copies src. The slim final stage copies /app including .venv, puts it on PATH, appends the corporate CA to certifi's bundle so outgoing HTTPS works behind the TLS-inspecting proxy, and runs uvicorn with 4 workers.
13. What does depends_on: condition: service_healthy guarantee, and what doesn't it?
Compose starts the API only after Postgres's healthcheck (pg_isready) passes. It doesn't help if Postgres dies later; for that, the pool's pool_pre_ping and the health endpoint's degraded status matter. It also only applies at up time, within one Compose project.
14. With 4 uvicorn workers and pool_size=20, how many Postgres connections can the API open?
Each worker is a separate process with its own lifespan and its own engine, so up to 4 × 20 = 80 (max_overflow is 0). Postgres's default max_connections is 100, and Airflow uses the same server. Scaling workers without shrinking pools will exhaust connections.
